## Method and exact commands

The operator runs `mise run pr:size -- origin/main` for a PR targeting `main`, or substitutes the upstream target for a stacked PR. The shell calls `git merge-base <target> <head>`, then `git diff --name-status -z -M <merge-base> <head>`, then `git show <revision>:<path>` for each available side. It compares LF-delimited blob lines with `difflib.SequenceMatcher(autojunk=False)`, retaining removed and added lines separately. A rename keeps both paths for exclusion checks. A deletion has an empty head side. The default head is `HEAD`, and `--head <revision>` selects another committed head.

The shell writes the full base and head contents and each changed-line fragment to temporary files with the side's original extension. For each nonempty sample it runs `scc --by-file --format json --gen --min --no-config --no-cocomo --no-complexity --no-gitignore --no-ignore --no-scc-ignore --count-unsupported <sample>`. For extensionless fragments it also passes `--count-as-pattern '*:<language>:<language>'`, using the language detected from the corresponding complete side. The full-side result supplies generated and minified flags. The fragment results supply removed and added `Code` values. The core first applies configured path exclusions and then binary, generated, and minified exclusions. Included code files count removed plus added `Code`. Included prose files count each nonblank removed or added line, including Markdown comments. Excluded files remain in JSON with raw line counts and a reason. Successful JSON goes to stdout; errors go to stderr. The command reports the total but leaves enforcement to issue #93.

Observed: `mise run check:pr-size-contract` printed one JSON row for each of the lockfile, generated, rename, deletion, comment-only, multiline-comment, documentation-only, mixed, minified, and over-limit fixtures. The over-limit fixture reports 801 raw additions, 801 units, and `"verdict": "fail"`. The other fixtures report `"verdict": "pass"`. The command exits 0 when fixture expectations hold. The case data is in `tests/fixtures/pr_size/cases.json`, and the ten per-file results are committed in `reports/inputs/pr-size-142-fixture-results.jsonl`.

## Method comparison and errors

Observed: replacing `value = 1` with `value = 2` gives one code line at both base and head. Their absolute count difference is zero, while the fragment method counts two changed code lines. The rename fixture records this balanced edit. The mixed fixture also counts two code lines even though its comment replacement and added blank line contribute zero.

Observed: changing `old text` to `new text` inside a JavaScript `/* ... */` block yields two fragment code units because the isolated fragments omit the comment delimiters. The complete files have the same `scc` code count. This is a known overcount. A base/head count difference would give zero for that edit, but it would also lose balanced code replacements. The fragment method is selected because added plus deleted work is the binding unit. The error is recorded for review rather than silently treated as an exact lexical classification.

Inference: a fragment from a multiline string or another syntax construct can also lose its enclosing context. `scc` generated detection can classify a prose page with a marker in its heading as generated. The counter does not reconstruct full-file parser state for isolated fragments. It fails when a nonexcluded text sample cannot be classified, while binary changes are listed with a `binary` exclusion reason. Binary byte accounting belongs to issue #93.
