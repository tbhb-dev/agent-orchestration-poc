## Review and creation contract

The selected store is Project 9 draft items. The source issue or PR records a reciprocal `Stub:` link. Its author comment contains only the proposed full issue body and supplies a stable `html_url`. A separate `tbhbbot` comment supplies the verdict URL. The body producer and the new-issue consumer both hash `gh api ... --jq .body` output, including the trailing output newline, under `set -o pipefail`, exactly as #90 specifies. The stub title and body producer hashes the `--jq '[.content.title,.content.body] | @json'` output. Both producers and the reviewer consumer use the same commands. An edited comment has unequal creation and update times and fails closed. A changed Project title or body changes its digest and invalidates approval. Deletion or incomplete reads fail closed. The source thread's latest valid verdict for that stub governs.

The documented GraphQL creation path is one `addProjectV2DraftIssue` mutation with `projectId`, `title`, and `body`, plus one read-back. The selected REST path is `POST /user/{user_id}/projectsV2/9/drafts`, one creation request, followed by `GET /users/tbhb/projectsV2/9/items/{item_id}` and one source comment. The live per-stub budget is the two complete paginated inventories plus one create, one read-back, and one source-comment write, with request count and `X-RateLimit-*` response headers recorded. A review adds two record reads, a source-thread comment listing, and one verdict write. Creation adds fresh reads, one REST issue POST, one issue GET, and one provenance comment. These are proposed bounds, not an observed live run. GraphQL request cost was not probed under the REST-only rule, so its rate-limit cost is unknown and no GraphQL path is selected for execution.

The synthetic [fixture](../../tests/fixtures/stub_policy/synthetic.md) gives stub, full-body snapshot, verdict, read-back, duplicate-search, and old-Backlog records. Its URLs, IDs, and logins are deliberately synthetic. No approval is inferred from ordinary issue comments without checking the source stub, exact body bytes, identity, timestamps, latest verdict, and #90 arbitration. The issue body preserves the approved snapshot. A separate issue comment carries the stub URL and digest because putting a digest of the body inside that same body would be self-referential.
