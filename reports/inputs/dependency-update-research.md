## Proposed limits and handoff

[documented] Renovate's `prConcurrentLimit` applies per repository to routine PRs. `vulnerabilityAlerts` bypasses that limit unless it has its own `prConcurrentLimit`. The [source configuration reference](https://github.com/renovatebot/renovate/blob/0dfb75020092789b7dc3f398e31259173f24b69f/docs/usage/configuration-options.md) explicitly describes separate budgets. [proposed] Set routine `prConcurrentLimit` to 2 and `vulnerabilityAlerts.prConcurrentLimit` to 1, with automerge disabled. These produce at most three simultaneous Renovate PRs when both limits work as documented. The coordinator counts any other open update proposals in the same repository and pauses or closes advisory proposals before dispatch if the total reaches three. A configuration validator and live trial must check the bound before activation.

[proposed] Package rules group by manager and update class. Routine patch and minor proposals may group within one ecosystem. Security fixes use the separate vulnerability route and never join routine changes. A major proposal is single-dependency unless every member is part of the same necessary major migration. No group mixes a major with unrelated changes. The coordinator reviews proposed diffs and splits a group that crosses stack rules, issue scope, or the PR size target.

[proposed] Renovate's PR is advisory. The coordinator selects or creates an open issue with a goal, allowed paths, evidence requirements, and exactly one compliant `area/`, `type/`, `phase/`, and `harness/` label, then dispatches a worker on an issue-number branch as the authorized implementer. The worker reads the proposed versions and upstream source, records exact pins and lockfiles, updates stack rules and conventions, and commits a research note link. The coordinator-owned implementation PR has a conventional title and body ending with an open `Refs` issue. A different-model `tbhbbot` review and all five required checks precede merge preflight. The generated PR receives no identity bypass and is never the merge vehicle under the current #89 contract.

[proposed] Installation, service credentials, repository policy, and any choice to make service-authored PRs mergeable belong to the operator and require a separate #83/#89 identity decision. #92 and #93 must establish branch and dependency gates before enablement. A real advisory proposal and a coordinator-owned update PR must demonstrate the complete gate before the service is called enabled. The #102 `lodash-es` alert repair is separate and does not establish this trial.
