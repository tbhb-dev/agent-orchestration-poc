## Record and search

Before recording deferred work, a defect, or a follow-up, search open repository issues by title and distinctive terms with `gh api 'search/issues?q=repo%3Atbhb%2Fagent-orchestration-poc+is%3Aissue+is%3Aopen+TERM&per_page=100' --paginate`. Enumerate all open issues with `gh api 'repos/tbhb/agent-orchestration-poc/issues?state=open&per_page=100' --paginate`, excluding entries with `pull_request`, so a search-result limit cannot hide a match. Then enumerate all Project 9 items with `gh api -H 'X-GitHub-Api-Version: 2022-11-28' 'users/tbhb/projectsV2/9/items?per_page=100' --paginate` and compare every `DraftIssue` title and body. Search each distinctive term and record the terms, page completion, match URLs, and disposition. An incomplete page or rate limit stops recording until the inventory is complete. Extend or link a matching issue or stub. A new stub is allowed only when no match covers the work.

The canonical stub is a Project 9 draft item in Backlog. Give it a conventional title. In the [stub template](https://github.com/tbhb/agent-orchestration-poc/blob/main/docs/briefs/stub-template.md), write two or three sentences of what and why, plus the source issue or PR URL and recording agent. Its canonical URL is the REST `item_url` returned by GitHub, with form `https://api.github.com/users/tbhb/projectsV2/9/items/<item-id>`. Put `Stub: <canonical Project item URL>` in the source PR body or issue comment and repeat that line in the final message. Check that the draft's Source URL points to this issue or PR and that the source text points back to the same draft. A stub has no repository issue number and cannot be dispatched.

Project 9 is user-owned. The documented REST creation route is `POST /user/{user_id}/projectsV2/9/drafts` with title and body. The documented GraphQL alternative is `addProjectV2DraftIssue(input: {projectId, title, body})`. These are one creation request each, followed by one read-back and one source-comment write. Use REST under the current access policy. Capture the returned numeric item ID and `item_url` on read-back. A later live trial must have a separately recorded coordinator target, authorization, request ceiling, and cleanup bounds.

## Author and review

The issue author expands the stub into the complete #84 body. Its sections are Goal, Context and links, Dependencies and paths, Acceptance criteria, Evidence required, Docs impact, and Out of scope. Include the Project stub URL, source URL, and author harness, model, and effort in Context and links. Post the full issue body as one new comment on the source issue or PR, without a wrapper. Its `html_url` is the stable draft-body URL. Do not edit that comment. Revisions use new author comments.

The producer hashes exactly the newline-ended output of `gh api repos/tbhb/agent-orchestration-poc/issues/comments/<draft-comment-id> --jq .body | shasum -a 256` under `set -o pipefail`, after checking the API exit status. The stub producer hashes exactly `gh api -H 'X-GitHub-Api-Version: 2022-11-28' users/tbhb/projectsV2/9/items/<item-id> --jq '[.content.title,.content.body] | @json' | shasum -a 256` under the same conditions. The reviewer re-reads both records and checks `created_at == updated_at` for the author comment. The reviewer records the two digests. The JSON output defines the bytes hashed for the title and body. The Project item remains editable.

Each verdict is a new issue comment by `tbhbbot` on the same source issue or PR. Its first line is `Stub review: ready` or `Stub review: changes needed`. It includes `Stub-URL`, `Draft-URL`, `Body-SHA256`, `Stub-SHA256`, and `Reviewer: <harness>, <model>, <effort>`. The comment's `html_url` is the immutable-verdict reference, provided its `updated_at` still equals `created_at`. A changed or deleted verdict, wrong account, same model as author, missing digest, incomplete read, or a later author revision refuses approval. The latest valid `tbhbbot` verdict for the stub is effective, including a later changes-needed verdict. The #90 three-changes verdict limit and newer coordinator arbitration comment apply to this source thread.

Before creation, the author repeats both producer commands and checks the latest verdict, all comment timestamps, and the draft's Backlog state. The approved body's complete bytes become the new issue body. After the REST creation, run `gh api repos/tbhb/agent-orchestration-poc/issues/<new-number> --jq .body | shasum -a 256` with `set -o pipefail` and compare it with `Body-SHA256`. Read `user.login` from the same issue. Only `tbhbagent` may create it. Add a new issue comment with `Approved-stub: <Project URL>`, `Approved-draft: <comment URL>`, `Approved-verdict: <comment URL>`, and `Body-SHA256: <digest>`. The body remains byte-for-byte equal to the approved snapshot. A mismatch or wrong author is an exception for the coordinator, with no automatic repair.

The coordinator verifies the source and issue links. After the read-back, the coordinator moves the created issue to Refinement and retires the draft. Only then may a fresh #90 issue review and coordinator-controlled status move it to Ready. Ready is capped at eight and means dispatchable now. Blocked parks work, and In review is not a status. Project changes are manual and not part of this policy PR.

## Transition and exceptions

The coordinator's [2026-09-27 direction](https://github.com/tbhb/agent-orchestration-poc/issues/161#issuecomment-5853040703) applies immediately to new unrefined work. Existing Backlog issues remain issues. Their approved refinement moves them to Refinement, without deletion or recreation. Report any issue created by the previously launched `issue-author-op26` run as an exception. Direct issue creation from an unrefined stub stops now. Before the full activation instant, use the current approved issue procedure for work already refined. Activation for the complete checker is recorded on #161 only after #90 and #183 are ready, as specified in [decision 0016](/decisions/0016-stub-refinement/).

After activation, `mise run issue:stub-exceptions -- --activated-at <UTC timestamp>` from #183 reports post-activation missing or stale approvals, wrong authors, reused verdicts, and incomplete API reads. It does not edit issues or Project fields. The coordinator reviews each exception and records its source and disposition. Uncertain or unauthorized creation goes to the operator. A later live trial needs a named draft and source thread, a bounded request count, separate coordinator authorization, and cleanup or rollback instructions before any write.
