## Decision

### Roles and authority

| Role | Allowed after cutover | Refused example |
| --- | --- | --- |
| Agent implementer and issue author, `tbhbagent` | Commits, pushes, issue and PR bodies, comments, implementer thread replies | Submitting its own approval as `tbhbbot` |
| Agent coordinator, `tbhbagent` | Dispatch notes, Project draft items and item field edits, ordinary reviewed merges | Merging a security-policy PR because the token has write access |
| Reviewer, `tbhbbot` | Review verdicts, review comments, issue-review comments, review thread resolution | Writing product code, ordinary merges, or operator arbitration |
| Configuration agent from #135, `tbhb` | Approved repository configuration through a restricted operation interface | Issue or PR prose, comments, reviews, Project item edits, or any PR merge |
| Human operator | Independent authorization, authoritative post-cutover `tbhb` comments, sensitive merges using `tbhbagent` transport | Treating an agent's same-account evidence as human consent |

Configuration means rulesets, branch protection, settings, labels, Actions settings and secret names, webhooks, collaborator access, and Project 9 configuration. Project item content and field values are agent communication. Project field definitions, views, and access are configuration. The configuration agent posts its explanatory prose through a separate `tbhbagent` operation, never through its `tbhb` interface. It can inspect and propose its own gated change but cannot authorize it or merge its PR.

The cutover record contains UTC timestamp T and effective main SHA C. Only comments whose API `user.login` equals `tbhb` and whose `created_at` is at or after T acquire operator authority by this rule. Earlier agent comments remain historical evidence, even if edited later. Text claiming to be the operator never changes authorship. Preserve comment ID, body digest, creation and edit timestamps. An edit invalidates a cached authorization and requires fresh confirmation.

An eligible comment from the operator overrides instructions in coordinator notes, reviewer verdicts, and briefs. Before a gated mutation, bind it to an independently authenticated operator-coordinator record. The channel is the operator's direct control session, outside GitHub agent prose. The operator confirms the exact action, target, and current state there. A comment alone cannot supply this second record because agents retain the token. This policy relies on detection and accepts worker access to the credential.

Keep three distinct authorization kinds: `approve-issue`, `merge-sensitive`, and `arbitrate-round`. Each record has an opaque ID, human-channel message reference, kind, repository and issue/PR target, exact operation and payload digest, expected current head/base or issue-body digest, relevant verdict URL, creation time, expiry, and unused/consumed state. Store records outside worker write access and pass verified plain values to policy checks. Refuse a record if its target or comment changed. Also refuse a record that has expired or was consumed, and stop on any failed read. Record the result and readback against that ID. An agent-authored record or arbitrary file with those fields is invalid.

For #90, `approve-issue` must follow the fresh ready verdict and bind its URL and exact body digest. For arbitration, require the exact command `Arbitration: authorize another round`, newer than the third changes-requested verdict, plus a record naming that verdict and the one additional round. A human command has no invented agent trailer. If a coordinator relays it as `tbhbagent`, #131's parser separates the final attribution block, but the relay cannot replace the independent record. #89 and #120 route sensitive changes to the operator regardless of GitHub write permission. Ordinary product code that handles credentials remains eligible for coordinator merge under the existing boundary.

### Explicit account selection

Select a process-local wrapper modeled on `scripts/reviewer-gh.sh`. Proposed code paths for #140 are `scripts/agent-gh.sh`, `src/agent_orchestration_poc/core/account_policy.py`, and `src/agent_orchestration_poc/shell/account_policy.py`. #135 consumes its restricted configuration entry point. Those paths need reservation in the successor issues before coding and are not edited here.

The wrapper accepts a role and a typed operation, not unrestricted shell text. Pure functions validate the role and canonical host/repository alongside the method, endpoint, payload, expected account, and required authorization. The shell resolves the requested account internally and checks `GET /user`. It then executes one operation with the same process-local credential. Remove inherited token overrides and debug settings, pin `github.com`, use a trusted executable and configuration path, disable aliases/extensions, and refuse caller-supplied authentication headers, external URLs, host overrides, executable hooks, or generic GraphQL. Token lookup or identity mismatch must never fall back to the active account.

For `tbhb`, allow only approved method/path/payload combinations. Examples are `PATCH /repos/tbhb/agent-orchestration-poc/labels/{name}` for a label description and operator-authorized `PUT /repos/tbhb/agent-orchestration-poc/rulesets/{id}` for a specified ruleset diff. Reject every issues, issue-comments, pulls, pull-review, merge, and git-ref mutation. Project configuration uses individually reviewed GraphQL operations with fixed operation text and validated Project ID, never arbitrary queries. Security settings, access, Actions permissions or secret names, webhooks, credentials, egress, and host changes require the operator record. Non-security label and presentation changes may consume coordinator authorization under #135.

[Documented] gh 2.100.0 supports named-account token lookup. `GH_TOKEN` overrides stored credentials, and keyring service names are based on the hostname. A separate `GH_CONFIG_DIR` changes file configuration but does not create a separate OS credential store. [Observed] An empty config directory refused the safe identity request in this environment, which does not establish isolation. The source and probes are recorded in `research/gates/agent-identity/gh-identity-probes.md`.

A wrapper constrains compliant callers and detects account mistakes. A reachable token and a worker-editable wrapper cannot confine a hostile worker. A fine-grained configuration token could exclude Issues and Pull requests permissions. Its permission model cannot express the complete operator contract, payload limits, human approval, or all Project operations. Do not claim that broad classic `repo` scope excludes communication. Select the wrapper plus detection for this cutover, as directed. Any future restricted token requires an endpoint permission audit and operator issuance.

Never expose credential lookup stdout to the agent, command line, trace, exception, log, or file. Pass it only in the child environment, suppress lookup diagnostics, and emit fixed failures. Child environments are still reachable to sufficiently privileged same-host processes. Disable shell tracing, `GH_DEBUG`, deprecated `DEBUG`, HTTP dumps, and crash dumps for credential handling. Log only operation IDs, effective login, safe target identifiers, status, and redacted digests.

### Signing and verification

New agent commits use author and committer `tbhbagent <agent@tonyburns.net>`. This is the proposed exact Git identity. The operator must verify that email on `tbhbagent` before activation. A GitHub login does not set Git author metadata. Reject inherited `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `EMAIL`, and configuration overrides that change the approved values. The pusher, author, committer, signer, and contributor trailers are separate facts.

Select OpenPGP through a narrow host signing service, conditional on the operator confirming the existing key format. Key format, fingerprint, subkey, account binding, and host isolation are untested here. Pin the full approved signing fingerprint and primary fingerprint in the operator-owned policy. Never select a key by email, a short ID, the first available key, or a mutable repository setting. A different key format requires a reviewed design update before activation.

The worker's Git signing adapter uses the documented `gpg.openpgp.program` interface but sends only a bounded commit payload to an operator-controlled service. The service runs under a separate OS principal or isolated host unavailable to worker processes. The operator transfers the existing private key to that boundary and removes worker-readable copies before signing is enabled. Workers receive neither private key material nor passphrases. Do not expose a general GPG-agent socket or an unlocked signing oracle.

For the initial cutover, the operator authorizes each exact unsigned commit payload digest in the independent channel. The service checks repository identity, allowed branch, parent SHAs, tree SHA, exact author/committer fields and message, payload size, policy version, expiry, and a one-use request ID. It reconstructs or compares the canonical payload bytes before signing. It refuses arbitrary files, tags, authentication challenges, different keys, changed parents, and replay. Rate limits and request logs bound abuse. The reply contains the detached signature and request ID only. These controls authorize only the signing operation. Merge authority and contributor attribution require their own evidence.

The adapter exits nonzero on denial, timeout, identity mismatch, malformed response, or verification failure. The adapter must never fall back to an unsigned commit. The worker verifies the resulting commit before push, using a verifier with only the operator-approved public trust material. A verification service may return the safe result when worker access to public material is restricted. Public trust material must come from the approved main/host policy, never the untrusted PR head. This design neither reads public/private keys nor runs signature commands.

[Documented] Git 2.55.0 provides `git verify-commit --raw <sha>` and `%G?`, `%GF`, `%GP` signature fields. The future verifier requires successful cryptographic verification, the exact approved signing and primary fingerprints, acceptable current key state, and exact author/committer metadata. GitHub REST corroborates linked `author.login` and `committer.login` as `tbhbagent` and `verification.verified=true` with reason `valid`. Missing mappings or verification data fail. GitHub's persistent badge can remain after key revocation, so the current local policy remains necessary. These commands would invoke a verification backend and are deferred to cutover, not executed in this PR.

| Commit case | Required treatment |
| --- | --- |
| Agent feature or empty provenance commit | Approved agent author, committer, signer, signature, and #131 trailers |
| Agent-created merge from main | Sign the new merge commit, validate both parents, and attribute substantive integration work |
| Inherited main history | Exclude commits reachable from recorded current main from the PR population, retain their original history |
| Human-only branch merge | No invented agent trailer, require a separately admitted human identity and valid signature or refuse pending operator policy |
| GitHub squash result | Verify separately as GitHub web-flow signing, bind the merge actor and returned SHA to the authorized PR head/base and exact title/body union |
| Open branch with unsigned commits | Old objects remain unsigned. Require an explicit migration decision and preserve published history |
| Valid signature from another key | Refuse despite GitHub's verified flag |

Issue #133 collects every commit reachable from the head but not current main, including the new merge-main commit, with complete API pagination and local ancestry corroboration. Recheck head/base afterward. `git merge --verify-signatures` checks only the side tip and cannot replace population verification. #131 controls the trailer union. GitHub's squash signer is not the agent key and is allowed only for the separately bound postmerge result. Pin the approved GitHub signing identity at cutover, preserve the PR's canonical body, and stop further merges if readback fails.

### Cutover and detection

The operator-only sequence and exact proposed changes are in `reports/inputs/agent-identity-design.md`. Prepare #131, #133/#139, #135, and #140 before #134. #89 consumes authorship, arbitration, and sensitive-merge routing. #90 consumes fresh issue approval and arbitration. #120 consumes fresh merge authorization. #134 owns activation and worker instructions. #135 owns configuration operations. #133 owns detection, with #139 supplying comment/review observations. These assignments extend the current issue bodies where the later operator notes require them.

Run detection in PR checks and on a five-minute schedule, plus before dispatch and merge. Report every post-T `tbhb` write outside configuration, including human comments. A report can be reconciled with an independent operator record but must not be silently excluded. Check actor API fields, agent role lines, issue/PR edits, reviews, comments, Project item changes, and configuration-operation receipts. Require complete pagination, durable cursors, overlap windows, and edit/deletion handling. Unknown actors, missing event coverage, API errors, stale runs, and changed records make coverage incomplete and stop dispatch. Project event coverage must be demonstrated before cutover, not inferred from a current snapshot.

If accidental `tbhb` use is found, pause agent writes, preserve redacted evidence, confirm affected authority with the operator, and revoke outstanding authorization records. The prepared stronger response is operator revocation of agent-reachable `tbhb` credentials, removal of their local copies, and reissuance into a separate operator OS account or host. A new `GH_CONFIG_DIR` alone is insufficient. Restrict configuration to a broker with named operations if restored. Rollback uses a reviewed operator-merged PR under the active policy, with exact separately authorized ruleset changes only when needed. Never restore `tbhb` as the agent default or disable detection silently.

### Security cross-check requirements

The operator control session must authenticate outside the worker OS identity. The service renders the exact action, target, state, and payload digest for confirmation instead of trusting an agent-written summary. Authorization storage uses the isolated service principal and atomic one-use consumption. The proposed host paths and permissions are in the operator plan. Until that service is ready, the independent record requirement fails closed. Commands requested through a `tbhb` comment require independent confirmation before execution if they have side effects or disclose data. Authorship still determines instruction precedence, subject to the accepted credential risk.

Repository-local signing settings are convenience defaults that a worker can override. Enforce signatures in the already-required `pr-body` check using verifier code and policy from a trusted base revision or operator service, never executable code from the PR head. Neutralize system/global Git configuration and use an isolated verification environment with explicit trusted backend and public policy. Changes to the verifier, detector, workflows, wrapper, trust material, or authorization service are security-policy changes and require operator merge. Refuse `%G?` values other than `G` and compare full fingerprints. Refresh public revocation data and policy at verification time, stop if freshness is unknown, and record the compromise cutoff when a key is withdrawn. GitHub key rotation requires an operator-approved policy update.

Detection receipts and event storage must be outside worker write access. Require an independently monitored heartbeat, durable event capture, and snapshots of configuration that can disable detection. Event subscriptions and host setup need exact operator approval under #134. Test change-and-revert, missing delivery, deleted comments, and revoked detector access. A personal repository may lack sufficient audit coverage, which remains untested. If complete coverage cannot be demonstrated, cutover remains blocked pending an operator decision on the documented gap. The five-minute poll alone is insufficient.

Drain includes the coordinator, scheduled tasks, launch agents, credential-helper users, and automation that might retain an old credential or instruction. Inventory these without reading secret values. Restart affected sessions with fresh policy and scrubbed environments before resumption. Reconcile `tbhbbot` review actions against recorded reviewer dispatches, flag mismatches, and admit automation actors only through an explicit purpose-specific catalog. Reviewer account separation remains a process control because its credential is reachable too. Project Ready transitions still require #90's fresh verdict and, for gated issues, operator authorization. Project Done transitions need recorded completion evidence, not a field edit as proof of completion.

Use an operator-owned installed wrapper with a pinned artifact digest. The repository scripts are development entry points, while active workers use the trusted installed path. Audit the proposed login token's permissions as the operator without disclosing its value and limit grants to the approved operations. The signing service admits only assigned feature branches and uses a dedicated agent signing key or subkey approved by the operator. It never signs directly for `main`. Inspect worker-readable backups and signing-agent caches during operator migration, and test access rather than assuming file modes suffice.

Before enabling signing, admit a separate operator recovery signer and account binding in trusted policy and rehearse a signed recovery PR with fresh review. If that route is unavailable, the operator may separately authorize removal of only `required_signatures`. Complete the reviewed recovery and restore the rule after verification. The operator enforces the pause and can revoke agent credentials or remove write access if agents do not stop. A compromise invalidates pending authorizations and requires review of commits within the affected interval even if GitHub still marks them verified. The required trusted verifier closes the policy gap while legacy work delays the additional signature ruleset.

## Consequences

The selected controls reduce accidental identity use but accept the reachable-token risk explicitly. Signing needs an isolated service and per-request human authorization before unattended workers can produce signed commits. The service and sandbox rehearsals are required before cutover and remain untested. If the operator declines that setup, the coordinator cannot dispatch signed workers. Open-PR handling and the exact public fingerprint values remain operator decisions, with no guessed defaults.
