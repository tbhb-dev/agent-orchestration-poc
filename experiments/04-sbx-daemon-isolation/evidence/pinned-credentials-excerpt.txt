    47	## Stored secrets
    48
    49	`sbx secret set` stores credential values or dynamic secret sources in your OS
    50	keychain, keyed on a service identifier. Built-in agents declare a fixed set of
    51	services. Custom kits can declare their own. The same `sbx secret set` flow
    52	works for both.
    53
    54	### Where secrets are stored
    55
    56	The store backing `sbx secret set` depends on your operating system:
    57
    58	- macOS: the system Keychain.
    59	- Windows: the Windows Credential Manager.
    60	- Linux: the Secret Service exposed by your desktop keyring, such as GNOME
    61	  Keyring or KDE Wallet.
    62
    63	The Ubuntu package depends on GNOME Keyring, so a standard desktop install
    64	needs no extra setup.
    65
    66	On Linux hosts without a running Secret Service — headless servers and some WSL
    67	setups — `sbx` falls back to a file under your user config directory
    68	`$XDG_CONFIG_HOME/com.docker.sandboxes`, which defaults to
    69	`~/.config/com.docker.sandboxes` when `$XDG_CONFIG_HOME` is unset. The fallback
    70	is automatic and needs no configuration. When you store a secret this way,
    71	`sbx` prints a notice:
    72
    73	```text
    74	No keychain detected - this secret will be stored on disk, protected by file permissions rather than a password
    75	```
    76
    77	`sbx` stores the file in a directory with `0700` permissions, the same
    78	file-permission model used for `~/.docker/config.json`. Any user or process that
    79	can read the file can retrieve the stored credentials, so treat the directory as
   430	## Credential bindings
   431
   432	A credential bindings file records which credential mechanisms and domains
   433	you've approved for each service. It lives at
   434	`~/.config/sbx/credentials.yaml`, or `%APPDATA%\sbx\credentials.yaml` on
   435	Windows.
   436
   437	Third-party kits that declare `schemaVersion: "2"` require an approved binding
   438	for each credential they use. `sbx` creates one interactively the first time you
   439	run such a kit (see [First-run approval](#first-run-approval)); you can also
   440	write entries by hand. Credentials declared only by embedded, built-in kits are
   441	authorized by provenance and don't need a binding.
   442
   443	Each entry under `bindings` is keyed by a
   444	[service identifier](#built-in-services) and approves one or both credential
   445	mechanisms:
   446
   447	- `apiKey` — approves injecting the service's stored API key. The value comes
   448	  from the [secret store](#stored-secrets) (`sbx secret set <service>`); the
   449	  binding records approval, it doesn't hold or locate the value.
