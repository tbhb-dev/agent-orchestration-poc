### Hook handler types and fields

Five handler types: `command`, `http`, `mcp_tool`, `prompt`, `agent` (agent hooks are marked experimental) [vendor-docs: hooks.md lines 404-412]. Common fields: `type`, `if` (a single permission-rule string such as `Bash(git *)`, evaluated only on tool events), `timeout` (seconds; defaults 600 for command/http/mcp_tool, 30 for prompt, 60 for agent; lowered to 30 on `UserPromptSubmit`, `PreModelSwitch`, `PostModelSwitch` and 10 on `MessageDisplay`; `SessionEnd` hooks share a 1.5 s budget raised to at most 60 s), `statusMessage`, `once` (honored only in skill frontmatter) [vendor-docs: hooks.md lines 420-431]. Command hook fields: `command`, `args` (exec form, no shell), `async`, `asyncRewake` (runs in background and wakes Claude on exit code 2), `shell` (`bash` or `powershell`) [vendor-docs: hooks.md lines 450-461]. HTTP hook fields: `url`, `headers`, `allowedEnvVars` [vendor-docs: hooks.md lines 505-513]. MCP tool hook fields: `server` (scoped `plugin:<plugin>:<server>` for plugin servers), `tool`, `input` with `${tool_input.file_path}` style substitution [vendor-docs: hooks.md lines 544-554]. Prompt and agent hook fields: `prompt` with `$ARGUMENTS`, `model` [vendor-docs: hooks.md lines 606-613]. All matching hooks run in parallel; the same handler defined in several settings files runs once [vendor-docs: hooks.md line 414].

Async hooks: `"async": true` is available only on `type: "command"`; async hooks cannot block or control behavior; output is delivered on the next conversation turn, except an `asyncRewake` hook exiting 2 wakes Claude immediately even when idle; `timeout` is not enforced on plain async hooks [vendor-docs: hooks.md lines 3668-3697, 3767-3769].

### Matchers

`"*"`, `""` or omitted matches all; a value containing only letters, digits, `_`, `-`, spaces, `,` and `|` is an exact string or `|`/`,`-separated list; anything else is an unanchored JavaScript regular expression (`Edit.*` also matches `NotebookEdit`; anchor with `^Edit$`) [vendor-docs: hooks.md lines 285-298]. `FileChanged` and `StopFailure` use a narrower exact set (letters, digits, `_`, `|`) [vendor-docs: hooks.md line 302]. MCP tools match by `mcp__<server>__<tool>` names, for example `mcp__memory__.*` [vendor-docs: hooks.md lines 296, 355].

### Input payload

Common input fields: `session_id`, `prompt_id` (UUID of the prompt being processed), `transcript_path` (written asynchronously, may lag), `cwd`, `scratchpad_dir`, `permission_mode` (`default`, `plan`, `acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`; Manual arrives as `default`), `effort` (object with `level`), `hook_event_name`; plus `agent_id` and `agent_type` when inside a subagent or `--agent` [vendor-docs: hooks.md lines 746-767]. `PreToolUse` adds `tool_name`, `tool_input`, `tool_use_id`, and for MCP tools an `mcp_server` object with `name` and `source` (requires 2.1.274+) [vendor-docs: hooks.md lines 1599-1603]. `PostToolUse` adds `tool_response` and optional `duration_ms` [vendor-docs: hooks.md lines 2000-2027]. File-tool `tool_input.file_path` is always absolute [vendor-docs: hooks.md line 1605]. Environment: hook commands run in their own session without a controlling terminal on macOS and Linux [vendor-docs: hooks.md line 742]; `CLAUDE_CODE_SESSION_ID` is set in hook subprocesses [vendor-docs: https://code.claude.com/docs/en/env-vars.md line 362]; `CLAUDE_CODE_BRIDGE_SESSION_ID` is set while Remote Control is connected [vendor-docs: hooks.md line 418]; `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` are exported to hooks and Bash for the session's cross-session inbox [vendor-docs: https://code.claude.com/docs/en/cross-session-messaging.md lines 237, 244].

### Output

### Rule syntax

Rules are `Tool` or `Tool(specifier)`; deny is evaluated first, then ask, then allow, first match wins [vendor-docs: settings-reference.md lines 1510-1514; permissions.md lines 85-99]. `Bash(*)` equals `Bash`; a bare deny removes the tool from context [vendor-docs: permissions.md line 97]. Bash wildcards: `*` matches any text including spaces; a trailing `*` also matches the bare command; `:*` suffix is equivalent to `*` only at the end [vendor-docs: permissions.md lines 136-181]. Parameter rules `Tool(param:value)` for deny and ask on any built-in tool, for example `Agent(model:opus)`, `Agent(isolation:worktree)`, `Bash(run_in_background:true)`; primary content fields (`command`, `file_path`, `path`, `url`) cannot be matched this way; MCP parameter rules only via `--disallowedTools` [vendor-docs: permissions.md lines 111-134]. Tool-name globs in deny and ask: `"*"`, `"mcp__*"`; allow globs only after a literal `mcp__<server>__` prefix [vendor-docs: permissions.md lines 183-197]. Read/Edit rules use gitignore-style path patterns with `//`, `~/`, `/` anchors (section at permissions.md lines 322-436). `WebFetch(domain:example.com)` [vendor-docs: permissions.md lines 108, 437]. MCP: `mcp__puppeteer`, `mcp__puppeteer__*`, `mcp__puppeteer__puppeteer_navigate` [vendor-docs: permissions.md lines 480-484]. `Agent(Explore)`, `Agent(my-custom-agent)` control which subagents may run [vendor-docs: permissions.md lines 490-506]. `Cd(...)` rules govern `/cd` only [vendor-docs: permissions.md lines 508-522]. ### Permission modes

`claude --help` lists `--permission-mode` choices `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan` [source: `claude --help`]. The docs table [vendor-docs: permissions.md lines 72-77]: `default` prompts on first use of each tool (labeled Manual; `manual` alias needs 2.1.200+); `acceptEdits` auto-accepts file edits and common filesystem commands (`mkdir`, `touch`, `mv`, `cp`) in working directories; `plan` reads and runs read-only commands, with classifier-approved commands when auto mode is available; `auto` auto-approves with background safety checks; `dontAsk` auto-denies everything that would prompt, including `AskUserQuestion`; `bypassPermissions` skips prompts except the actions no mode auto-approves. Bypass is refused in `--restricted` sessions [vendor-docs: https://code.claude.com/docs/en/permission-modes.md line 569].

Auto mode, exactly as documented [vendor-docs: permission-modes.md]: "A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read. Explicit ask rules still force a prompt" (line 278). With 2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions on every plan and provider; earlier only on Pro, Max, Team (lines 11, 280). The classifier also reviews each `SendMessage` to another agent before delivery, in auto mode and in plan mode while the classifier reviews commands (line 282; requires 2.1.222+). Critical-path `rm`/`rmdir` (for example `rm -rf /`, `rm -rf ~`) are not reviewed by the classifier and follow the critical-path rules (line 284, section 631). Auto mode nudges Claude to keep working without clarifying questions (line 286). Availability requires a supported model, and organizations can turn it off with `permissions.disableAutoMode: "disable"` in managed settings, which also removes it from the Shift+Tab cycle (lines 292-313). Server-side classifier review: sessions can ask the server to review as part of model requests instead of sending their own classifier requests; fallback to local classifier when the server does not review; `CLAUDE_CODE_AUTO_MODE_SERVER=0` disables and `1` forces on for `-p`/SDK sessions on direct API (lines 317-330). ### `--restricted` and `--bare`

`--restricted` (2.1.248+): removes the built-in tools that run commands or code (Bash, PowerShell, REPL and other code-running tools) and WebFetch unless `--tools` names them; ignores user, project and local settings files (managed settings and `--settings` still apply; add `--strict-mcp-config` to skip MCP servers); confines file tools to the working directories including `--add-dir`; refuses `bypassPermissions`; lets only a person or the configured permission handler approve writes to settings, git and tool-configuration files [source: `claude --help`; vendor-docs: cli-reference.md line 122; permission-modes.md lines 569, 599]. `claude agents --restricted` starts dispatched sessions in restricted mode [source: `claude agents --help`].

`--bare`: skips hooks (settings and plugin hooks; built-in features unaffected), LSP, plugin sync, attribution, auto-memory, background prefetches, keychain reads, and CLAUDE.md auto-discovery; sets `CLAUDE_CODE_SIMPLE=1`; auth is strictly `ANTHROPIC_API_KEY` or `apiKeyHelper` via `--settings`; skills still resolve via `/skill-name`; context must be passed explicitly with `--system-prompt[-file]`, `--append-system-prompt[-file]`, `--add-dir`, `--mcp-config`, `--settings`, `--agents`, `--plugin-dir` [source: `claude --help`]. ### How the sandbox works

macOS uses Seatbelt; Linux and WSL2 use bubblewrap; WSL1 and native Windows are not supported [vendor-docs: sandboxing.md lines 17, 562-568]. On Linux and WSL2 the sandbox needs `bubblewrap` (filesystem isolation) and `socat` (relay to the sandbox network proxy); the `/sandbox` Dependencies tab lists which of `ripgrep`, `bubblewrap`, `socat` and the seccomp filter are missing [vendor-docs: sandboxing.md lines 65-88]. Ubuntu 24.04+ needs an AppArmor profile for `bwrap` when `kernel.apparmor_restrict_unprivileged_userns` is 1 [vendor-docs: sandboxing.md lines 95-112]. Filesystem defaults: write to cwd, `--add-dir` and `additionalDirectories`, and the per-user temp dir; read the whole machine except denied paths (credential files such as `~/.aws/credentials` are readable unless `sandbox.credentials` or `denyRead` block them); protected paths include `.claude` settings, skills, agents, commands, hooks directories, `.mcp.json`, shell startup files, `.git/hooks` and `.git/config`, most of `~/.claude` [vendor-docs: sandboxing.md lines 491-516]. Network access goes through a proxy running outside the sandbox; no domains pre-allowed by default; the proxy does not terminate TLS by default; corporate proxies via `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` in the settings `env` block so background agents also get them [vendor-docs: sandboxing.md lines 518-535]. Two sandbox modes: auto-allow (sandboxed commands run without prompts; deny rules, critical-path `rm`, and content-scoped ask rules still apply; a bare `Bash` ask rule is skipped) and regular permissions mode [vendor-docs: sandboxing.md lines 126-149]. The unsandboxed retry escape hatch (`dangerouslyDisableSandbox`) goes through the regular permission flow, or the classifier in auto mode; disable with `allowUnsandboxedCommands: false` [vendor-docs: sandboxing.md lines 151-160]. The sandbox isolates Bash subprocesses only; Read, Edit, Write use the permission system; subagents share the parent's sandbox configuration [vendor-docs: sandboxing.md lines 726-737]. Security limitations include domain fronting through the hostname-only allowlist, Unix socket escalation, and the weaker nested sandbox on Linux [vendor-docs: sandboxing.md lines 707-718]. Strict sandbox mode also covers `!` shell-mode commands in a background session and in a Linux session with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` [vendor-docs: sandboxing.md lines 160-164].

Stream-json message types documented: `system` with subtypes `init` (first event; carries model, tools, MCP servers, plugins, `plugin_errors`, and a `capabilities` array such as `interrupt_receipt_v1`, `interrupt_cancel_queued_v1`), `api_retry`, `permission_denied`, `compact_boundary`, `informational`, `worker_shutting_down`, `plugin_install`, `status`, `task_notification`, `task_started`, `task_progress`, `task_updated`, `background_tasks_changed`, `hook_started`, `hook_progress`, `hook_response`, `thinking_tokens`, `files_persisted`, `local_command_output`, `commands_changed`; `assistant`; `user` (subagent messages carry `parent_tool_use_id`); `result` (subtype `success` and others, with `permission_denials`, `deferred_tool_use`, `origin`); `stream_event` (partial message chunks with `--include-partial-messages`); `prompt_suggestion` [vendor-docs: headless.md lines 171-230; https://code.claude.com/docs/en/agent-sdk/typescript.md lines 1268-1310 for the full `SDKMessage` union and the `subtype` lines at 1414, 1618, 1705, 1726, 1743, 1757, 1780, 4931, 4946, 4993, 5009, 5028, 5101, 5134, 5158, 5190, 5213, 5229, 5267, 5283]. `--include-hook-events` adds hook lifecycle events; `SessionStart` and `Setup` events are always included [vendor-docs: cli-reference.md line 97]. `--forward-subagent-text` forwards subagent text and thinking blocks with `parent_tool_use_id` at every nesting depth (2.1.211+) [vendor-docs: headless.md lines 190-201].

`--input-format stream-json` accepts newline-delimited `{"type":"user","message":{"role":"user","content":...}}` objects, where content may be a string or content blocks including images [vendor-docs: https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode.md lines 100-130]. The bidirectional control protocol uses `control_request` messages with `{ type: "control_request", request_id, request }` and matching `control_response` replies that echo `request_id` [vendor-docs: typescript.md lines 769, 1131-1133]. Documented control requests: `initialize` (sent once at start and again by `reinitialize()`; carries `hooks`; the response wrapper carries `pending_permission_requests`, requires 2.1.268+), `interrupt` (with optional `cancel_queued: true`, 2.1.219+; receipt lists `still_queued`/`cancelled`), `set_permission_mode` (via `setPermissionMode()`), and `can_use_tool` permission requests that the host answers [vendor-docs: typescript.md lines 613-621, 758-800, 1796]. A full table of wire-level control request subtypes was NOT FOUND in the docs; the TypeScript reference documents them through the `Query` methods (`interrupt()`, `setPermissionMode()`, `setModel()`, `applyFlagSettings()`, `rewindFiles()`, `initializationResult()`, `reinitialize()`, `getContextUsage()`, `readFile()`, `reloadSkills()`, `readMcpResource()`) [vendor-docs: typescript.md lines 566-633]. Permission prompts in SDK mode are answered by the `canUseTool` callback, which returns `{ behavior: "allow", updatedInput }` or `{ behavior: "deny", message }` (Python `PermissionResultAllow`/`PermissionResultDeny`); it never fires for auto-approved tools; `AskUserQuestion` also routes through it [vendor-docs: https://code.claude.com/docs/en/agent-sdk/user-input.md lines 11-61, 205-212]. Without an SDK, `--permission-prompt-tool <mcp tool>` names an MCP tool that handles prompts in non-interactive mode [vendor-docs: cli-reference.md line 111]. Exit behavior: SIGTERM exits 143 leaving the turn unfinished; SIGINT or `interrupt()` ends the turn; background Bash tasks are killed about 5 s after the final result, while background subagents and workflows keep `claude -p` open up to a 10-minute idle ceiling (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`) [vendor-docs: headless.md lines 65-84].

### Background daemon and `--bg`

### 6. Cross-session and multi-agent features

### Agent teams

Agent teams are experimental and disabled by default; enable with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in the environment or a settings `env` block [vendor-docs: agent-teams.md lines 10, 50-58; env-vars.md line 286]. One session is the team lead; teammates are separate Claude Code instances with their own context windows; Claude launches a teammate when it calls the Agent tool with a `name` while teams are enabled, unless the call is a fork or passes `isolation`; no confirmation is asked [vendor-docs: agent-teams.md lines 13, 223-225]. Spawning teammates requires an interactive session; in `-p` and SDK sessions a named subagent runs as an ordinary subagent [vendor-docs: agent-teams.md line 62]. Architecture: team lead, teammates, shared task list, and a mailbox per agent at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; team config at `~/.claude/teams/{team-name}/config.json` (removed at session end) and task list at `~/.claude/tasks/{team-name}/` (persists); team name is `session-` plus the first eight characters of the session ID [vendor-docs: agent-teams.md lines 227-251]. Display modes via `teammateMode` (`in-process` default, `auto`, `tmux`, `iterm2`) or `--teammate-mode` [vendor-docs: agent-teams.md lines 96-125; settings-reference.md lines 4986-5005]. Permissions: teammates start with the lead's mode except `dontAsk`; prompts appear in the lead session; plan approvals are granted automatically; messages between agents are marked as coming from another Claude session and cannot convey user consent; the auto-mode classifier reviews each inter-agent message before delivery [vendor-docs: agent-teams.md lines 281-294]. Hooks: `TeammateIdle` (exit 2 keeps the teammate working) and `TaskCompleted` (exit 2 prevents completion) [vendor-docs: agent-teams.md lines 209-215]. Shared task list uses file locking; `CLAUDE_CODE_TASK_LIST_ID` shares a task list across sessions [vendor-docs: agent-teams.md line 195; env-vars.md line 388; interactive-mode.md line 641]. `teammateDefaultModel` was removed in v2.1.234 [vendor-docs: agent-teams.md line 153]. `CLAUDE_CODE_TEAM_TEARDOWN_PARK_TIMEOUT_MS` bounds non-interactive teardown wait [vendor-docs: env-vars.md line 389]. Limitations: no session resumption of in-process teammates, one team per session, no nested teams, no background subagents from in-process teammates, lead is fixed, split panes need tmux or iTerm2 [vendor-docs: agent-teams.md lines 467-479]. Publicly documented: yes (agent-teams page).

### Cross-session messaging (SendMessage and ListAgents)

Requires 2.1.224+ on macOS and Linux (including WSL 2) and 2.1.234+ on native Windows; on by default with nothing to enable [vendor-docs: cross-session-messaging.md lines 10, 297]. Claude discovers targets with `ListAgents` and sends with `SendMessage`; the user can `@`-mention a session (2.1.232+) [vendor-docs: cross-session-messaging.md lines 28, 42]. `ListAgents` shows subagents in the session, agent-team teammates, your other local sessions (only those that bind an inbox socket), your cloud sessions and Remote Control sessions on other machines while this session is connected to Remote Control (labeled `Remote Control`, with `offline` when the connection dropped) [vendor-docs: cross-session-messaging.md lines 108-116; tools-reference.md line 35]. `/list-agents` (alias `/peers`) shows the listing to the user [vendor-docs: cross-session-messaging.md line 307]. Delivery: on this machine over a per-session Unix domain socket (named pipe on Windows) never via Anthropic servers; to other machines through Anthropic servers over that machine's Remote Control connection; to cloud sessions through Anthropic servers; container-to-host and WSL-to-native-Windows cannot reach each other [vendor-docs: cross-session-messaging.md lines 133-149]. The socket lives in a private per-user directory `/tmp/cc-socks-<uid>` and is exported as `CLAUDE_CODE_MESSAGING_SOCKET` with `CLAUDE_CODE_MESSAGING_TOKEN` for scripts posting to their own session [vendor-docs: cross-session-messaging.md lines 232-256]. `notify_when_idle` (2.1.236+): a `SendMessage` input that subscribes to one notice when a local session next goes idle or exits; only the main conversation can subscribe and only to local sessions; the subscription expires after 12 hours [vendor-docs: cross-session-messaging.md lines 79-106]. Inbound control: `crossSessionInbound` is `accept`, `hold`, or `refuse` (2.1.224+); when unset, Claude Code decides per message from the two sessions' permission-mode classes, holding messages from bypassing senders in prompting receivers and holding everything in bypassing receivers unless the sender also bypasses; at most 100 held messages; a `-p` session cannot show the dialog and expires held messages after `dialogExpiry` (5 minutes default), so unattended `-p` workers should be started with `crossSessionInbound: accept` in `--settings` [vendor-docs: cross-session-messaging.md lines 184-224; settings-reference.md lines 4911-4932]. `isolatePeerMachines: true` requires approval before any message leaves the machine, even in bypass mode (2.1.224+) [vendor-docs: settings-reference.md lines 4951-4967]. Turning it off: deny rules on `SendMessage` and `ListAgents` plus `crossSessionInbound: refuse` [vendor-docs: cross-session-messaging.md lines 279-293]. `[ref]` disambiguation: NOT FOUND in the cross-session-messaging page as fetched (grep for `[ref]` returned nothing there); the only description of a `[ref]` suffix is in the `ListAgents` tool description that Claude Code presents to the model at runtime, which is not a citable public source. Publicly documented: yes (cross-session-messaging page, tools-reference rows for `SendMessage` and `ListAgents`).

### What a hook can return

- [source] Universal JSON output fields (`codex-rs/hooks/src/engine/output_parser.rs:1-7`): `continue` (bool), `stopReason`, `suppressOutput`, `systemMessage`. ### Trust model

- [source] Each discovered handler gets a key `<source>:<event_key>:<group_index>:<handler_index>` (e.g. `/Users/x/.codex/hooks.json:pre_tool_use:0:0`, `declarations.rs:88-97`, `config_rules.rs:80`) and a hash of its normalized identity (`discovery.rs:766-791`). Trust status (`HookTrustStatus`) is `Trusted` if builtin or the stored `trusted_hash` equals the current hash, `Modified` if a different hash is stored, `Untrusted` if none, `Managed` for System/MDM/EnterpriseManaged/legacy-managed layers (`discovery.rs:793-811, 823-835`). A handler runs only if enabled and (`bypass_hook_trust` or status is `Managed`/`Trusted`) (`discovery.rs:713-717`).

### Background execution and how the model is woken

- [source] Unified exec processes outlive a single call: `thread/backgroundTerminals/list|clean|terminate` in the app-server, `background_terminal_max_timeout` config key (schema), `/ps` in the TUI (release 0.157 PR #48101 "Show multiline command previews in `/ps`"). The model polls with `write_stdin`/`exec_command` on the session id; no push notification is injected for terminal output (NOT FOUND in `hook_runtime.rs`/`session`).
- [source] Subagents: V1 `wait_agent` subscribes to child status channels and blocks until a final status or `timeout_ms` (`handlers/multi_agents/wait.rs:95-178`). V2 `wait_agent` waits on the session input-queue activity watch (`Mailbox` or `Steer`) with clamped `min/max/default_wait_timeout_ms` (`handlers/multi_agents_v2/wait.rs:53-95`, `core/src/session/input_queue.rs:83-86`).
- [source] In V2 the parent does not have to call `wait_agent`: child completion and `send_message`/`followup_task` are delivered as `Op::InterAgentCommunication` (`core/src/agent/control.rs:249-280`), enqueued into the parent's mailbox (`core/src/session/handlers.rs:79-95`), rendered as user-role `MESSAGE`/`NEW_TASK` fragments (`core/src/context/inter_agent_message.rs:7-27`) or a completion message built from `AgentStatus` (`core/src/session_prefix.rs:19-38`), and drained at the next sampling point or, when `trigger_turn` is set, by starting a new turn on an idle parent (`handlers.rs:86-93`, `input_queue.rs:166-206`). Post-0.157.1 commit `f92655d07f` "Preempt model responses when new user input arrives" and feature `defer_mailbox_preemption` (schema) refine this. Release note 0.156.0: "Preserve streamed answers ... when subagents finish" (`rust-v0.156.0.md:12`).

### hooks.json structure

Top-level keys are hook names; each maps to an object with optional `enabled` (default true) and event arrays [source: hooks.md lines 15-79]. Tool events (`PreToolUse`, `PostToolUse`) use groups of `{ "matcher": <regex>, "hooks": [handler, ...] }`; `PreInvocation`, `PostInvocation`, `Stop` take a flat list of handlers and ignore matchers [source: hooks.md lines 85-106]. Matcher examples: `"*"` or `""` matches all tools, `"run_command"` exact, `"run_command\|view_file"` either, `"browser_.*"` prefix; tool names are the step type lowercased with the `CORTEX_STEP_TYPE_` prefix removed [source: hooks.md lines 108-114]. Handler fields: `type` (only `"command"`), `command` (run via `sh -c` on Unix, `cmd /c` on Windows, `~` expanded, working directory is the directory containing `hooks.json`), `timeout` in seconds default 30 [source: hooks.md lines 120-128]. Hooks from multiple named entries or plugins for the same event merge and run sequentially [source: hooks.md lines 58-61].

### Stdin payload

All payload keys are camelCase protojson [source: hooks.md lines 137-138]. Common fields: `conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`, `modelName`; the transcript and artifact paths use `antigravity-cli/` for the CLI [source: hooks.md lines 140-157]. Per event: `PreToolUse` adds `toolCall.name`, `toolCall.args`, `stepIdx` (lines 166-179); `PostToolUse` adds `stepIdx` and `error` when the tool failed (lines 225-233); `PreInvocation` and `PostInvocation` add `invocationNum`, `initialNumSteps` (lines 243-251, 277); `Stop` adds `executionNum`, `terminationReason` (`model_stop`, `max_steps_exceeded`, `error`), `error`, `fullyIdle` (true when all background tasks are done) (lines 299-308) [source: hooks.md]. The binary contains the payload key strings `conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`, `modelName` as exact lines [source: binary strings].

### Permission and execution modes

### What the imported research established

The peering research found: send_message is filesystem-backed, dropping JSON into the recipient's `messages/` queue; delivery happens at the recipient's next turn boundary, bundled chronologically in a `<SYSTEM_MESSAGE>` block; invalid recipients fail synchronously; messages persist while the recipient is unloaded; there are no steering, priority, list, edit, delete, or idempotency controls; and unsigned payloads written by a foreign process are ignored because the tool injects a `sourceMetadata.tool.thinkingSignature` [third-party: imported research, `AGY_PEERING.md` lines 7-34, `agy-peering-results.md` lines 69-120]. Its recommended external integration is either `agy --conversation <id> --print "<msg>"` (takes over the session, conflicts if the UI is open) or spawning `agy --new-project --print "Use the send_message tool to send ... to <id>"` to obtain a signed message [third-party: imported research, `AGY_PEERING.md` lines 42-54]. Read receipts can be polled in `read.json` [same, lines 56-65]. The session research established the brain layout, two transcript files, the hook payload fields, and subagent fan-out [third-party: imported research, `ANTIGRAVITY_SESSION_MANAGEMENT.md` lines 7-11, 19-28, 47-53].

What current sources add that the research did not record: the docs now state a `send_message` recipient may be "any conversation id" [vendor-docs: /docs/subagents?tab=cli], which is consistent with the research's observation but is now documented; the `@<subagent>` prompt syntax (1.2.9) [changelog line 22]; the `messages/undelivered/` directory [source]; message payload fields `priority` and `hideFromUser` [source]; the `schedule` tool's sender-conditioned wake [changelog line 372]; worktrees moving to the app data directory [changelog line 19]; the `deny_unless_prior_grant` hook decision [vendor-docs: /docs/hooks]; and the `WAITING` and `RUNNING` result statuses in stream-json [vendor-docs: /docs/cli/headless/]. Cross-process messaging between two independent top-level agy sessions via a documented public API (socket, HTTP, CLI subcommand): NOT FOUND in any docs page fetched or in `agy --help`; the only documented cross-session paths are the model-side `send_message` tool with a conversation id, resuming with `--conversation <id> -p`, and driving a session through Remote Control's companion UI.
