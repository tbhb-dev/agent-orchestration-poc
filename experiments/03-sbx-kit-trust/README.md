# BV-05: sbx kit routing and server trust

## Decision

**Partial investigation, property acceptance pending.** The fourth attempt created clean and public-kit sandboxes on the operator's installed sbx and observed a working guest-to-receiver TLS tunnel, negative certificate controls, renewal after restart, and non-consuming waits through 300 seconds. The required fake credential was not bound, so proxy injection and its upstream TLS verification hop remain untested. The kit alone has not been shown sufficient for credential-injecting HTTPS; no security property, backend profile, or real-harness cell is qualified. Issue #229 remains open. [Fourth-run notes](evidence/sbx-run-4/notes.md), [ledger](evidence/sbx-run-4/ledger.txt), [receiver log](evidence/sbx-run-4/receiver.jsonl), and [issue criteria](https://github.com/tbhb-dev/agent-orchestration-poc/issues/229) separate these results from property acceptance.

## Attempts and topology

The [first read-only attempt](evidence/read-only.md) and [second operator-state attempt](evidence/operator-state-attempt.md) preceded Docker sign-in. The second could not read effective settings or authenticate and did not run a stateful probe. The [third command ledger](evidence/installed-sbx-run/ledger.txt) records the approved setting change, kit validation, blocked creates, and host-only requests. It does not contain the original receiver launch, restart, certificate-verification, or receiver-cleanup commands. Their exact historical invocations and output were not retained. The [fresh host-only replay](evidence/installed-sbx-run/host-replay.txt) supplies an independently executed recipe for those steps, not missing history from the sbx attempt. The third attempt found an uninitialized global policy. The fourth found `default-deny-all` already present. The [fourth-run notes](evidence/sbx-run-4/notes.md) attribute this to likely operator initialization, but the intervening change is not recorded as an observation.

The fourth run used sbx v0.45.1 on macOS 26.5.1 arm64, the `shell` agent, `docker/sandbox-templates:shell-docker`, a disposable CA, and a receiver on `127.0.0.1:18443`. It did not run an integrated Claude Code or Codex harness in a sandbox. The executor issued the PKI and kit, then checked host rejection without the CA. After toggling `kit.allowLocalKits`, the executor created `bv05-clean` and `bv05-kit` headlessly from `/dev/null`. Guest curl and policy probes followed. The executor renewed the leaf and restarted the kit sandbox before measuring waits. The exact commands and exit codes are in the [ledger](evidence/sbx-run-4/ledger.txt), with the [PKI manifest](evidence/sbx-run-4/pki-manifest.json) and [receiver log](evidence/sbx-run-4/receiver.jsonl) recording fingerprints and SNI.

**Observed topology:** both guests resolved `host.docker.internal` to `fe80::1` and set `HTTPS_PROXY=http://gateway.docker.internal:3128`. The proxied guest dial reached `fd61:8f11:ddb2::2:3128`. The proxy policy log named `localhost:18443`. An allowed `forward-bypass` request reached the loopback receiver with SNI `host.docker.internal`, TLSv1.3, and no Authorization header. The receiver's loopback bind and its request log support an inference that the proxy's upstream dial reached host `127.0.0.1:18443`. A direct `--noproxy '*'` dial was logged as `transparent`. The guest verified the receiver leaf on these tunnel paths. The proxy passed through that TLS session. The proxy's upstream certificate verification name under credential injection is untested. [Ledger](evidence/sbx-run-4/ledger.txt), [receiver log](evidence/sbx-run-4/receiver.jsonl), and [notes](evidence/sbx-run-4/notes.md).

## Reproduce the host-only fixture

From the repository root, run:

```sh
mise exec -- bash experiments/03-sbx-kit-trust/host-replay.sh
```

The script creates a disposable `/private/tmp/bv05-host-replay.XXXXXX` directory, uses `PYTHONSAFEPATH=1` and `mise exec -- python` to issue the CA and leaves and generate a public kit, then runs `mise exec -- openssl verify` with `-CAfile` and `-verify_hostname localhost`. It launches `fixture.py serve` on `127.0.0.1:18453` with explicit `--root`, `--leaf`, `--port`, `--log`, and `--deliveries` flags. After trusted and untrusted curl requests, it restarts the receiver with `--client-ca` and sends requests with and without a client certificate. It prints the receiver log and removes the scratch directory on exit. The script never calls sbx or changes a trust store. The [captured replay](evidence/installed-sbx-run/host-replay.txt) records its output and exit results for expected verification failures. Port 18453 must be free.

The installed-sbx run used port 18443 and private material under `/private/tmp/bv05-pki`. Only public certificates, certificate fingerprints, and redacted request markers were committed. The [fixture](fixture.py) supplies `pki`, `kit`, and `serve` subcommands. Its `serve` mode records receiver SNI, TLS version, client-certificate fingerprint, header names, and a truncated digest of any authorization value. The `/wait` endpoint holds without consuming delivery state, while `POST /deliver` provides a positive control. The host replay focuses on the missing receiver lifecycle and certificate-verification record. The original [ledger](evidence/installed-sbx-run/ledger.txt) and [receiver log](evidence/installed-sbx-run/receiver.jsonl) retain the bearer and wait simulations.

## Cleanup and limits

**Fourth-run start and end, observed:** the daemon was running at both observations, `sbx ls --json` was empty, global `default-deny-all` and `local-policy` rows matched, the full settings hash was `0477633d77404d7c39490df322dc92a5aa0f84181b2eec02debd4b3d2a9af0f4`, and `kit.allowLocalKits` was `true` from `default`. While the kit sandbox existed, `sbx policy ls` showed its scoped allows instead of the `default-deny-all` row, though global `sbx policy check network` still reported implicit default deny. The original rows reappeared after removal. The daemon status and `sbx daemon start` process were unchanged across the run. The [ledger](evidence/sbx-run-4/ledger.txt) also records a `sandboxd` PID at the start, which is a different process from the `sbx daemon start` PID in the [notes](evidence/sbx-run-4/notes.md). They identify different processes.

**Undo results, observed:** `sbx settings unset kit.allowLocalKits` exited 0 after the disabled-setting probe, returning its source and full settings hash to the starting values. After the receiver stop, port 18443 had no listener. An initial `sbx rm bv05-clean bv05-kit < /dev/null` exited 1 because confirmation needed a terminal. `sbx rm --force bv05-clean bv05-kit` exited 0 and the next sandbox list was empty. The executor used only read-only global policy commands and left the daemon running. The conditional process-scoped host bundle was deferred. The [ledger](evidence/sbx-run-4/ledger.txt) and [notes](evidence/sbx-run-4/notes.md) record these commands. The template image cache was not checked before the run, and stored secrets, binding files, and trust stores were not read at either boundary, so their before/after states are unknown. The fixture's `/private/tmp` PKI and kit cleanup is not recorded. [Notes](evidence/sbx-run-4/notes.md), [ledger](evidence/sbx-run-4/ledger.txt).

The [versions record](versions.md) distinguishes fourth-run observations from earlier pins. The open next step is a separately approved fake-credential binding and injection test: only that path can show whether the proxy ends guest TLS and accepts the receiver's BV-05 leaf on its upstream TLS check. A process-scoped host bundle remains conditional on locating a kit-only failure at that hop. This inference comes from the tunnel behavior and unbound credential. Upstream trust remains untested. [Fourth-run notes](evidence/sbx-run-4/notes.md), [ledger](evidence/sbx-run-4/ledger.txt).
