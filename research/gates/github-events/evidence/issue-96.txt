Goal\n\nGive agents `receive`, `ack`, publish confirmation, and status and roster reads through a relay in `agentd`, so no agent credential ever holds JetStream API access. Design decision from the reviews of PR #82, 2026-09-26.\n\n## Context and links\n\nThe messaging sketch (`design-sketch/04-messaging-and-shared-context.md`) has each agent use its own durable pull consumer. Two reviews of PR #82 showed that this cannot be made safe with subject permissions. The first found that JetStream publish acknowledgments let one agent cause a publication on another agent's subject. The second, a Sonnet 5 cross-check, granted a test agent only `$JS.API.CONSUMER.MSG.NEXT.<stream>.<agent>` and had it set the pull request's reply subject to another agent's message subject. The server delivered stored content onto that subject with no permission error, because server-internal deliveries do not check the destination against the requester's permissions (`server/consumer.go` and `server/stream.go` in nats-server v2.15.0, cited in the review). The sender-name-in-subject rule is the identity property the whole bus rests on, so it wins. PR #82 keeps agents without any `$JS.API.>` or `$JS.ACK.>` grant and with publish acknowledgments disabled. The `agentctl` worker for #27 (draft PR #86) confirmed that agents therefore cannot receive, ack, or read status and roster yet.\n\n## Dependencies and paths\n\nDepends on PR #82 merging.
