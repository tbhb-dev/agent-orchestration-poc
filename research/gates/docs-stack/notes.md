# Docs stack research gate notes

Raw notes for issue #8, gathered 2026-09-26 before any docs-site configuration (issue #9). Codex writes the conventions page from these notes; this file is evidence, not the page.

## How to read the evidence labels

Every claim carries one of three labels. `[verified]` means the claim was read in a clone at the recorded SHA or produced by a command whose output is quoted; the citation follows the label. `[inferred]` means the claim follows from verified facts but was not executed here, and the docs-site item must confirm it. `[recommendation]` marks a judgement for the coordinator to accept or reject.

Clone paths and SHAs are listed once in `versions.md` in this directory. Citations below use the short SHA.

`[verified]` The official `examples/basics` template at `3ec633b` contains `astro.config.mjs`, `package.json`, `tsconfig.json`, `public/`, `src/assets/`, `src/content.config.ts`, and `src/content/docs/` with `index.mdx`, `guides/example.md`, and `reference/example.md`. Its `package.json` depends on `@astrojs/starlight ^0.42.4`, `astro ^7.2.10`, and `sharp ^0.35.3`, with scripts `dev: astro dev`, `build: astro build`, `preview: astro preview`, and `astro: astro`. `[verified]` `tsconfig.json` in the template extends `astro/tsconfigs/strict`, includes `.astro/types.d.ts` and `**/*`, and excludes `dist`. Source: `examples/basics/tsconfig.json` at `3ec633b`.

`[verified]` The `astro.config.mjs` shape is `defineConfig({ integrations: [starlight({ title, social, sidebar })] })` with `// @ts-check` at the top. Source: `examples/basics/astro.config.mjs` at `3ec633b`, and `docs/src/content/docs/manual-setup.mdx` at the same SHA, which states `title` is the only required option.

`[verified]` Content collections are configured in `src/content.config.ts` (not the Astro 4 location `src/content/config.ts`), with a `docs` collection built from `docsLoader()` from `@astrojs/starlight/loaders` and `docsSchema()` from `@astrojs/starlight/schema`. Source: `docs/src/content/docs/reference/configuration.mdx` section `Configure content collections` and `examples/basics/src/content.config.ts` at `3ec633b`. The Astro docs confirm `src/content.config.ts` is the special file name for build-time collections (`withastro/docs@99dba9d` `src/content/docs/en/guides/content-collections.mdx`, section `Defining build-time content collections`).

`[verified]` `docsLoader()` loads Markdown, MDX, and Markdoc files from `src/content/docs/` and ignores file names starting with `_`. By default file names are slugified (lowercased, special characters removed); a custom `generateId()` can override that. Source: `reference/configuration.mdx` section `docsLoader()` at `3ec633b`.

`[verified]` `docsSchema({ extend })` accepts a Zod schema or a function returning one. Since Astro 6, `z` must be imported from `astro/zod`, not from `astro:content` or `astro:schema`, and Astro 6 uses Zod 4 (string formats like `z.string().email()` moved to `z.email()`). Source: `withastro/docs@99dba9d` `src/content/docs/en/guides/upgrade-to/v6.mdx` sections `Zod 4` and `Deprecated: astro:schema and z from astro:content`.

### Frontmatter fields

`[verified]` `title` is the only required field. Optional fields: `description`, `slug`, `editUrl`, `head`, `tableOfContents`, `template` (`doc` or `splash`), `hero`, `banner`, `lastUpdated` (a YAML timestamp or boolean), `prev`, `next`, `pagefind`, `draft`, and `sidebar` with `label`, `order`, `hidden`, `badge`, and `attrs`. Source: `docs/src/content/docs/reference/frontmatter.md` at `3ec633b`.

`[verified]` `sidebar` frontmatter applies only to autogenerated links and to items declared with `slug`, never to items declared with `link`. `draft: true` pages are excluded from production builds and from autogenerated groups, and cannot be referenced by `slug` in the sidebar config. Source: same file, sections `sidebar` and `draft`.

### Sidebar configuration

`[verified]` A sidebar is an array of items. Each item is a `link` plus `label`, a `slug` (or a bare string shorthand), a group with `label` and `items`, or `{ autogenerate: { directory, collapsed?, attrs? } }`. Groups take `collapsed` and `badge`; links take `badge` and `attrs`. Autogenerated groups sort by file `id` alphabetically, and subdirectories become subgroups labelled by directory name. Source: `docs/src/content/docs/guides/sidebar.mdx` and `reference/configuration.mdx` section `sidebar` at `3ec633b`.

`[verified]` With no `sidebar` config at all, Starlight autogenerates the whole sidebar from the directory structure, labelling groups with raw directory names. Source: `guides/sidebar.mdx` section `Default sidebar`.

`[recommendation]` For the sections Project, Workflow, Research, Experiments, Design, Decisions, Guides, Retros, and Devlog: use explicit top-level groups with human labels and an `autogenerate` item inside each, one per directory under `src/content/docs/`, so that adding a page never requires an `astro.config.mjs` edit while the group labels stay capitalised and ordered. Retros and Devlog carry dated file names, so their `autogenerate` order is chronological; if the newest-first order is wanted for Retros, pages set `sidebar.order` in frontmatter. The Devlog entry is a `link` item to the blog index (see answer 3), not an `autogenerate` group. Shape:

```js
sidebar: [
  { label: 'Project', items: [{ autogenerate: { directory: 'project' } }] },
  { label: 'Workflow', items: [{ autogenerate: { directory: 'workflow' } }] },
  { label: 'Research', items: [{ autogenerate: { directory: 'research' } }] },
  { label: 'Experiments', items: [{ autogenerate: { directory: 'experiments' } }] },
  { label: 'Design', items: [{ autogenerate: { directory: 'design' } }] },
  { label: 'Decisions', items: [{ autogenerate: { directory: 'decisions' } }] },
  { label: 'Guides', items: [{ autogenerate: { directory: 'guides' } }] },
  { label: 'Retros', collapsed: true, items: [{ autogenerate: { directory: 'retros' } }] },
  { label: 'Devlog', link: '/devlog/' },
],
```

`[verified]` This mixed shape (explicit groups, autogenerated contents, and one `link` item pointing at a plugin route) is what the Starlight docs site and the `starlight-blog` docs site both use: `withastro/starlight@3ec633b` `docs/astro.config.mjs` and `HiDeoo/starlight-blog@19e7832` `docs/astro.config.ts` (`{ label: 'Demo', link: '/blog/' }`).

### Other configuration options worth knowing

`[verified]` `lastUpdated: true` reads Git history and is wrong on shallow clones; `editLink.baseUrl` builds "Edit this page" links; `markdown.headingLinks` (default true) adds anchor links; `markdown.processedDirs` extends Starlight's Markdown processing to other directories; `plugins` takes Starlight plugins; `expressiveCode` configures or disables code blocks; `pagefind` configures search; `prerender` defaults to true. Source: `reference/configuration.mdx` at `3ec633b`.

`[verified]` Starlight sets the active theme as `data-theme="light"` or `data-theme="dark"` on the `html` element; its own CSS selects on `[data-theme='light']` and `[data-theme='dark']`. Source: `packages/starlight/src/style/props.css` lines 123 to 124, `style/util.css` lines 45 to 48, and `style/reset.css` line 19 at `3ec633b`. This matters for Mermaid theming in answer 2.

### What changed in 0.40 to 0.42 that older training data gets wrong

`[verified]` All items below come from `packages/starlight/CHANGELOG.md` at `3ec633b` unless noted.

- 0.40.0 added support for Astro 6.4 and the Sätteri Markdown processor and raised the minimum Astro to 6.4.5. Sätteri is opted into with `markdown: { processor: satteri() }` from `@astrojs/markdown-satteri`.
- 0.41.0 added Astro 7 support and dropped Astro 6; it also dropped Chromium before 111 and Safari before 16.4.
- 0.42.0 ships compiled JavaScript with `.d.ts` files instead of TypeScript sources; removed the never-used `tagline` config option; raised minimums to Astro 7.2.10, `@astrojs/markdown-satteri` 0.4.0, and `@astrojs/markdown-remark` 7.3.0; rewrote the mobile menu toggle (the `<starlight-menu-button>` element, its `aria-expanded` attribute, and the `data-mobile-menu-expanded` body attribute are gone; use `.sl-menu-button` and `:popover-open`); and dropped Chromium before 116, Safari before 17.0, and Firefox before 125.
- 0.42.1 to 0.42.4 are patches: sidebar rendering optimisations for large sidebars, new icons, a table-of-contents freeze fix when a `<PageTitle>` override lacks `id="_top"`.

`[verified]` Astro-level changes that older training data gets wrong, from `withastro/docs@99dba9d` `src/content/docs/en/guides/upgrade-to/v7.mdx` and `v6.mdx` and `withastro/astro@7a698ca` `packages/astro/CHANGELOG.md` (entry for PR #16966):

- Astro 7 renders `.md` and `.mdx` with Sätteri by default; `@astrojs/markdown-remark` is no longer installed. The legacy `markdown.remarkPlugins`, `markdown.rehypePlugins`, and `markdown.remarkRehype` options still work but now require `@astrojs/markdown-remark` to be installed and imply the `unified()` processor. The supported way to use remark or rehype plugins is `markdown: { processor: unified({ remarkPlugins, rehypePlugins }) }` from `@astrojs/markdown-remark`.
- Astro 7 replaced the Go compiler with a Rust compiler that errors on unclosed tags and no longer auto-corrects invalid HTML nesting.
- Astro 7 reserves `src/fetch.ts` for advanced routing (set `fetchFile: null` to disable).
- Astro 7 changed `compressHTML` default to `'jsx'`, which strips whitespace between inline elements; add `{" "}` where a space is needed.
- Astro 7 upgraded to Vite 8. Astro 6 dropped Node 18 and 20, moved to Zod 4, removed legacy content collections entirely (`legacy.collections` is gone, only the Content Layer API remains), removed `Astro.glob()` and `<ViewTransitions />`, and deprecated `astro:schema` and `z` from `astro:content` in favour of `astro/zod`.
- Astro 7 removed the `astro db`, `astro login`, `astro logout`, `astro link`, and `astro init` commands (CHANGELOG entry for 7.0.0-beta.3).

`[verified]` Starlight supports both processors. `packages/starlight/src/integrations/markdown-plugins.ts` at `3ec633b` checks `isSatteriProcessor(processor)` and pushes mdast and hast plugins, or `isUnifiedProcessor(processor)` and pushes remark and rehype plugins, and throws for any other processor with the message to switch to `satteri()` or `unified()`. The unified integration (`./remark-rehype`) is loaded lazily and resolves to `null` when `@astrojs/markdown-remark` is not installed.

## Answer 2: Mermaid at build time

`[verified]` Mermaid cannot render without a browser DOM. The `mermaid` 12.0.0 changelog states the Node requirement exists only for dependency resolution "as mermaid requires a browser". Source: `mermaid-js/mermaid@69778e6` `packages/mermaid/CHANGELOG.md` under `## 12.0.0`. Every build-time option therefore drives a headless browser; the choice is between doing that at build time in CI or shipping Mermaid to the reader's browser.

`[verified]` The Starlight plugin catalogue lists exactly one Mermaid entry, `astro-mermaid` by joesaby, described as "Client-side render Mermaid content in Markdown code blocks". Source: `docs/src/content/docs/resources/plugins.mdx` lines 321 to 323 at `3ec633b`. A grep for `mermaid` across `packages/starlight/src` at that SHA returns nothing: Starlight has no built-in Mermaid support.

### Option A: rehype-mermaid (build time, unified processor)

`[verified]` `rehype-mermaid` 3.0.0 (npm, last modified 2026-01-28; clone `remcohaszing/rehype-mermaid@cab7b87`, tag v3.0.0 plus 13 commits) is a rehype plugin that replaces `<pre><code class="language-mermaid">` and `<pre class="mermaid">` with rendered output. Strategies: `inline-svg` (default, an inline `<svg>`), `img-svg` and `img-png` (an `<img>` with a data URI, optionally wrapped in `<picture>` with a `dark` variant), and `pre-mermaid` (leaves a `<pre class="mermaid">` for client-side rendering). Source: `README.md` and `package.json` in that clone.

`[verified]` Outside a browser it renders through `mermaid-isomorphic` 3.1.0, which drives Playwright; both READMEs say to run `npm install playwright` and `npx playwright install --with-deps chromium`. `rehype-mermaid` declares `playwright: 1` as an optional peer dependency. Sources: `remcohaszing/rehype-mermaid@cab7b87` `README.md` section `Installation` and `package.json`; `mise exec -- npm view mermaid-isomorphic readme` (3.1.0, peer `playwright: 1`). Playwright on npm is 1.63.0 (`npm view playwright version`).

`[verified]` `rehype-mermaid` is a unified plugin, so on Astro 7 it requires `@astrojs/markdown-remark` 7.3.1 and `markdown: { processor: unified({ rehypePlugins: [rehypeMermaid] }) }`. Source: the Astro v7 upgrade guide section `New default Markdown processor: Sätteri` and `markdown-content.mdx` section `When to use Unified` at `withastro/docs@99dba9d`; `npm view @astrojs/markdown-remark version` gives 7.3.1.

`[verified]` The Starlight maintainer's current recipe (HiDeoo, 2024-05-02, Starlight discussion 1259, comment 9300105) is: install `rehype-mermaid`, add it to the Astro `markdown` rehype plugins, and nothing else, because since Starlight 0.22 Expressive Code is a rehype plugin and no longer consumes `mermaid` fences before rehype plugins run. That recipe predates Astro 7, so today it reads `processor: unified({ rehypePlugins: [rehypeMermaid] })` instead of `rehypePlugins: [rehypeMermaid]`. Source: `gh query graphql` on discussion 1259; the closed Starlight issue 1682 (2024-03-27) points at the same thread.

`[inferred]` Plugin order still works in Starlight's favour: Starlight splices the Expressive Code integration into the integrations array after itself (`packages/starlight/src/index.ts` at `3ec633b`, the `config.integrations.splice(selfIndex + 1, 0, ...integrations)` line), so Expressive Code's hook runs after the user's processor options exist and pushes its rehype plugin after `rehypeMermaid`. The docs-site item must confirm a `mermaid` fence renders as SVG and not as a highlighted code block.

`[verified]` Dark and light themes: `inline-svg` renders one colour scheme, and the `dark` option is supported only by `img-svg` and `img-png`, which emit a `<picture>` whose `<source media="(prefers-color-scheme: ...)">` follows the operating system, not Starlight's `data-theme` toggle. Source: `rehype-mermaid` `README.md` sections `inline-svg` and `dark`, and `src/rehype-mermaid.ts` lines 130 to 180 at `cab7b87`; Starlight's theme attribute is cited in answer 1. `colorScheme` is read from a `color-scheme` meta tag or defaults to `light`, and `mermaidConfig` can set a theme such as `neutral`.

`[verified]` A render failure throws unless `errorFallback` is provided, in which case the block is replaced or removed. Source: `README.md` section `errorFallback` at `cab7b87`. So with the default options a broken diagram fails `astro build`, which gives the docs site the fenced-Mermaid validation the plan lists as a phase 1 mechanical-check candidate, for pages inside `docs/` at least.

`[verified]` Dependency cost: `rehype-mermaid` pulls `mermaid-isomorphic`, `hast-util-from-html-isomorphic`, `hast-util-to-text`, `mini-svg-data-uri`, `unified`, `unist-util-visit-parents`, and `vfile` (its `package.json` at `cab7b87`), plus `playwright` 1.63.0 and a Chromium download in CI. It is compatible with Node 18 or greater and with `mermaid` code blocks processed by `remark-rehype`, which includes MDX (`README.md` section `Compatibility`).

`[verified]` A related package, `remark-mermaidjs` 7.0.0, is older (last modified 2025-03-24) and has the same Playwright peer; the Starlight discussion thread records its author advising against it for Astro, so it is not evaluated further.

### Option B: astro-mermaid (client-side, Sätteri-native)

`[verified]` `astro-mermaid` 2.1.0 (npm, last modified 2026-06-24; GitHub release v2.1.0 on 2026-06-24) is an Astro integration that registers a Sätteri mdast plugin on Astro 7, remark and rehype plugins on Astro 6.4 to 6.x, and legacy options before that, then renders in the reader's browser with theme switching on `html[data-theme]` or `body[data-theme]`. It must be listed before `starlight()` in `integrations`. Source: `mise exec -- npm view astro-mermaid readme` sections `Astro Compatibility` and `Integration Order`.

`[verified]` Its peer dependencies are `astro >=4`, `mermaid ^10.0.0 || ^11.0.0`, and `@mermaid-js/layout-elk ^0.2.0` (`npm view astro-mermaid peerDependencies`). Mermaid on npm is 12.0.0 (published 2026-09-10), so a fresh install must pin `mermaid` to 11.x or hit `ERESOLVE`; open issue 75 (2026-09-15) asks for v12 support. Open issue 74 (2026-08-08) reports that on Astro 7 with `@astrojs/mdx` 7, Mermaid fences in `.mdx` files render as escaped text while the build succeeds. Source: `gh query` on `joesaby/astro-mermaid` issues and releases.

`[verified]` Cost: the reader downloads Mermaid at view time (the 12.0.0 changelog notes the single-file build grows by about 500 kB gzipped with ELK bundled; 11.x is smaller but unsupported going forward), diagrams are absent without JavaScript, and nothing validates diagrams at build time. Theme switching does track Starlight's toggle, which is its one advantage over option A.

### Option C: mermaid client-side by hand

`[verified]` `mermaid` 12.0.0 exposes `mermaid.initialize({ startOnLoad })` and `mermaid.run({ querySelector })` for rendering `<pre class="mermaid">` elements in the browser; ELK is now bundled and the default layout for flowcharts, so diagrams laid out with dagre in 11.x look different unless `layout: dagre` is set. Source: `mermaid-js/mermaid@69778e6` `packages/mermaid/src/docs/config/usage.md` and `packages/mermaid/CHANGELOG.md` under `## 12.0.0`. Wiring this into Starlight means writing the fence-to-`<pre class="mermaid">` transform (a Sätteri mdast plugin or `rehype-mermaid` with `strategy: 'pre-mermaid'`) plus a script in `head` that re-runs on theme change. It is the most work for the same drawbacks as option B.

### Mermaid CLI for a repository-wide check

`[verified]` `@mermaid-js/mermaid-cli` 12.0.0 (npm, modified 2026-09-24) peers on `puppeteer ^25.0.0` and requires Node `>=22.13.0`, so it also needs a Chromium download. It is a separate concern from site rendering: the phase 1 tooling item's "Mermaid CLI check over every fenced mermaid block" covers Markdown outside `docs/` as well.

### Recommendation

`[recommendation]` Use option A: `rehype-mermaid` 3.0.0 with `strategy: 'inline-svg'`, `@astrojs/markdown-remark` 7.3.1 as the `unified()` processor, and `playwright` 1.63.0 with `pnpm exec playwright install --with-deps chromium` in the docs CI job. Reasons: diagrams are static SVG in the built HTML, so they need no JavaScript, print correctly, and are searchable; a broken diagram fails the build instead of failing silently in the reader's browser; and the maintainer of Starlight endorses the setup. The trade is a Chromium install in CI (cache the Playwright browser directory), the switch from Sätteri to unified for the docs site (Starlight supports both, and `starlight-blog` depends on both `@astrojs/markdown-remark` and `satteri`), and diagram colours that do not follow the site's theme toggle. For colours, set `mermaidConfig: { theme: 'neutral' }` so one rendering reads well on both backgrounds; if the coordinator wants toggle-aware colours instead, the fallback is `strategy: 'img-svg'` with `dark: true`, which follows the operating system preference rather than the toggle. Option B is rejected for now because its peer range excludes Mermaid 12 and its MDX rendering on Astro 7 has an open bug.

## Answer 3: starlight-blog for the devlog

`[verified]` `starlight-blog` 0.30.0 (npm, modified 2026-09-21; clone `HiDeoo/starlight-blog@19e7832`, tag `starlight-blog@0.30.0`) declares `peerDependencies` of `@astrojs/starlight: >=0.42.0`, and its 0.30.0 changelog entry says the minimum Starlight is now 0.42.0. 0.27.0 added Astro 7 and Sätteri support. It depends on `@astrojs/markdown-remark ^7.2.0`, `@astrojs/mdx ^7.0.0`, `@astrojs/rss ^4.0.18`, and `satteri ^0.10.3`. Source: `packages/starlight-blog/package.json` and `packages/starlight-blog/CHANGELOG.md` at `19e7832`; `mise exec -- npm view starlight-blog version peerDependencies`.

`[inferred]` The `@astrojs/mdx ^7.0.0` dependency sits next to Starlight's `@astrojs/mdx ^8.0.0`; pnpm installs both copies and the Starlight-registered one is the integration that runs, but the docs-site item should check `pnpm why @astrojs/mdx` and the build log for duplicate-integration warnings.

`[verified]` Installation: add `starlightBlog()` to Starlight's `plugins`, and extend the `docs` schema with `docsSchema({ extend: (context) => blogSchema(context) })` from `starlight-blog/schema`. Posts are Markdown or MDX files under `src/content/docs/<prefix>/`, where `prefix` defaults to `blog`; the multiple-instances guide confirms each instance reads the subdirectory named after its prefix, and `libs/content.ts` filters entries by `fileRelativePath.startsWith(prefix + '/')`. Source: `docs/src/content/docs/getting-started.mdx`, `guides/multiple-instances.mdx`, and `packages/starlight-blog/libs/content.ts` lines 99 to 101 at `19e7832`.

`[verified]` Configuration options: `title` (default `Blog`), `prefix` (default `blog`), `navigation` (`header-start`, `header-end` default, or `none`; the header options override Starlight's `SiteTitle` or `ThemeSelect` components and add a mobile-menu link), `postCount` (5), `recentPostCount` (10), `authors` (global authors keyed by id), `prevNextLinksOrder`, `metrics` (reading time, word count), `rss` and `structuredData` (both default on when Astro `site` is set). Source: `docs/src/content/docs/configuration.md` at `19e7832`.

`[verified]` Post frontmatter: `title` and `date` (a YAML timestamp) are required; optional `lastUpdated`, `tags` (string list), `excerpt`, `authors` (an id from the global config, an inline object with `name` plus optional `title`, `picture`, `url`, or a list of either), `featured`, `draft`, `cover`, and `metrics`. Posts list newest first by `date`. Source: `docs/src/content/docs/guides/frontmatter.md` and `guides/authors.md` at `19e7832`.

`[verified]` On blog pages the plugin replaces the sidebar with recent posts, featured posts, and tags; the docs sidebar is untouched elsewhere. The plugin's own docs site adds the blog to the docs sidebar with a plain link item. Source: `getting-started.mdx` feature list and `docs/astro.config.ts` at `19e7832`.

### The dated-pages fallback

`[verified]` Without the plugin, `src/content/docs/devlog/YYYY-MM-DD.md` pages with `title` and an `autogenerate` group give a chronological list oldest first (autogenerate sorts by file id), no index page unless one is written by hand, no tags, no RSS, and no per-post dates beyond what the page body says. Source: Starlight `guides/sidebar.mdx` section `Autogenerated links` at `3ec633b`.

### Recommendation

`[recommendation]` Use `starlight-blog` 0.30.0 with `prefix: 'devlog'`, `title: 'Devlog'`, `navigation: 'none'`, and a `{ label: 'Devlog', link: '/devlog/' }` sidebar item, so the Devlog sits in the sidebar with the other sections and the header is not overridden. Entries live in `src/content/docs/devlog/YYYY-MM-DD-<slug>.md` with `title`, `date`, and `tags`; `authors` names the harness and model that did the work (a global author per harness, for example `codex` and `claude`), which the plan says is how attribution is recorded instead of commit trailers. The plugin fits the pinned Starlight exactly (its floor is the same 0.42.0 that Starlight is on), so the dated-pages fallback is not needed; keep it only as the documented escape hatch if a future Starlight bump lands before the plugin catches up, which its changelog shows happening within a release or two each time.

## Answer 4: package management

### pnpm version

`[verified]` pnpm on npm: `dist-tags.latest` is 12.6.0 (published 2026-09-22); 12.7.0 exists on npm and as a GitHub release dated 2026-09-25, and `mise ls-remote pnpm` lists 12.5.1, 12.6.0, and 12.7.0. pnpm 12 is a native executable that does not need Node after install; installing through npm needs Node 22.13 or newer. Sources: `mise exec -- npm view pnpm dist-tags`, `npm view pnpm@12.7.0 version`, `gh query repos/pnpm/pnpm/releases`, `pnpm/pnpm.io@e7dc3d4` `docs/installation.md`.

`[verified]` The mise registry entry for `pnpm` uses `aqua:pnpm/pnpm` first and `npm:pnpm` second, detects `pnpm-lock.yaml` and `pnpm-workspace.yaml`, and reads `package.json` as an idiomatic version file. Source: `jdx/mise@fdfa0ef` `registry/pnpm.toml`. mise reads `devEngines.packageManager` first and then the top-level `packageManager` field, but only when `idiomatic_version_file_enable_tools` includes `pnpm`. Source: `docs/lang/node.md` section `Package-manager versions in package.json` at `fdfa0ef`.

### Workspace shape

`[verified]` A workspace needs `pnpm-workspace.yaml` at the repository root with a `packages` list; since 12.7.0 pnpm also converts a root `workspaces` field into that file. All pnpm settings live in `pnpm-workspace.yaml` (the settings page is the same document). Source: `pnpm/pnpm.io@e7dc3d4` `docs/workspaces.md`.

`[verified]` pnpm 10 and later refuse to run dependency build scripts that have not been approved; `allowBuilds` in `pnpm-workspace.yaml` maps package names to `true` or `false`, and under the default `strictDepBuilds` an install fails with `ERR_PNPM_IGNORED_BUILDS` when it reaches an unreviewed build. The Starlight repo sets `allowBuilds: { esbuild: false, sharp: false }`, and `starlight-blog` adds `unrs-resolver: false`. Sources: `docs/settings/build.md` section `allowBuilds` at `e7dc3d4`; `withastro/starlight@3ec633b` `pnpm-workspace.yaml`; `HiDeoo/starlight-blog@19e7832` `pnpm-workspace.yaml`.

`[recommendation]` Root `pnpm-workspace.yaml`:

```yaml
packages:
  - docs

allowBuilds:
  esbuild: false
  sharp: false
```

`[inferred]` `playwright` (for `rehype-mermaid`) has a postinstall step in some versions; if `pnpm install` reports it under ignored builds, add `playwright: true` to `allowBuilds` rather than `dangerouslyAllowAllBuilds`. The browser download itself is the separate `playwright install` command, never a postinstall.

`[verified]` The root `package.json` needs `"private": true`, the `packageManager` field, and no dependencies of its own; `docs/package.json` carries `astro`, `@astrojs/starlight`, `starlight-blog`, `rehype-mermaid`, `@astrojs/markdown-remark`, `playwright`, `sharp`, and the `astro` scripts, mirroring `examples/basics/package.json` at `3ec633b`.

### Lockfile handling in CI

`[verified]` `--frozen-lockfile` defaults to `true` in CI (detected through the `CI` environment variable and the `ci-info` list) and `false` elsewhere; when true, pnpm fails if the lockfile is missing or out of sync with the manifests. Since pnpm 11, CI installs also fail when the lockfile was written by a newer pnpm major. Source: `pnpm/pnpm.io@e7dc3d4` `docs/cli/install.md` section `--frozen-lockfile` and `docs/continuous-integration.md`.

`[verified]` The documented GitHub Actions setup is `pnpm/setup@v2` with `runtime: node@24` and `cache: true`, which installs pnpm from the `packageManager` field, installs Node, runs `pnpm install`, and caches the store; `install: false` opts out of the install step. Corepack is no longer recommended because it starts Node before pnpm on every call. Source: `docs/continuous-integration.md` section `GitHub Actions` at `e7dc3d4`.

`[recommendation]` In CI run `pnpm install --frozen-lockfile` explicitly (the default is right, but the explicit flag is a rule a reader can check) and commit `pnpm-lock.yaml`. If the tooling item uses mise in CI rather than `pnpm/setup`, `mise install` provides pnpm and Node from `mise.toml` and the same `pnpm install --frozen-lockfile` follows.

### Biome 2.5 coverage of the site

`[verified]` Biome on npm is 2.5.14, matching the clone `biomejs/biome@088164f` (tag `@biomejs/biome@2.5.14` plus 75 commits). The mise registry `biome` entry uses `aqua:biomejs/biome` then `npm:@biomejs/biome`. Sources: `npm view @biomejs/biome version`; `jdx/mise@fdfa0ef` `registry/biome.toml`.

`[verified]` `files.includes` is a list of globs; a `!` prefix ignores, and a `!!` prefix force-ignores so the scanner never indexes the directory, which the changelog recommends for output folders such as `build/` and `dist/`. `files.experimentalScannerIgnores` is deprecated in favour of `!!`. `vcs.useIgnoreFile: true` makes Biome skip anything in `.gitignore`. Sources: `packages/@biomejs/biome/configuration_schema.json` (`FilesConfiguration` and `VcsConfiguration` descriptions) and `CHANGELOG.md` entry for PR #7359 at `088164f`.

`[verified]` `.astro` files get partial support by default: the `AstroFileHandler` extracts only the JavaScript between the `---` fences and hands it to the JavaScript handler. Full template support exists behind `html.experimentalFullSupportEnabled`, which the schema describes as "Enables full support for HTML, Vue, Svelte, and Astro files". Sources: `crates/biome_service/src/file_handlers/astro.rs` and `file_handlers/mod.rs` line 1349 (`partial support of vue/svelte/astro`), and `HtmlConfiguration` in the schema at `088164f`.

`[recommendation]` Biome covers `docs/astro.config.mjs`, `docs/src/content.config.ts`, any `.ts` or `.js` under `docs/src/`, `docs/package.json`, and `docs/tsconfig.json`. Force-ignore `docs/.astro/` (generated types and content-layer cache), `docs/dist/` (build output), and `node_modules/`; with `vcs.useIgnoreFile: true` those come for free once they are in `.gitignore`, but list them under `files.includes` as `!!docs/.astro/**` and `!!docs/dist/**` anyway so the rule does not depend on the ignore file. Leave `html.experimentalFullSupportEnabled` off for now: the site has no custom `.astro` components at first, and the phase 5 frontend gate can revisit it. `.md` and `.mdx` content stays with rumdl and Vale, and `pnpm-lock.yaml` and `pnpm-workspace.yaml` stay with ryl. `tsconfig.json` is a well-known JSONC file for Biome; if `biome check` complains about its comments, set `json.parser.allowComments` for it through an override rather than turning comments on globally.

## Answer 5: build and tasks

`[verified]` `astro dev` starts the development server; `astro build` writes static files to `dist/` by default, configurable through `outDir` (default `./dist`, relative to the project root) or the `--outDir` flag; `astro preview` serves the build; `astro check` type-checks `.astro` and `.ts` files and needs `@astrojs/check` plus `typescript`. Common flags include `--root`, `--config`, `--site`, `--base`, `--port`, `--host`, and `--verbose`. Sources: `withastro/docs@99dba9d` `src/content/docs/en/reference/cli-reference.mdx` and `reference/configuration-reference.mdx` section `outDir`.

`[verified]` `@astrojs/check` 0.9.10 peers on `typescript ^5.0.0 || ^6.0.0`; TypeScript on npm is 7.0.2 and the newest 6.x is 6.0.3. `[verified]` mise tasks can set `dir` so the command runs in `docs/`; the `npm` backend documentation says to keep application dependencies in `package.json` and run them through the package manager, not through `npm:` tools. Source: `jdx/mise@fdfa0ef` `docs/dev-tools/backends/npm.md`.

### Link checking

`[verified]` `starlight-links-validator` 0.26.0 (npm, modified 2026-09-02; clone `HiDeoo/starlight-links-validator@b725855`, tag 0.26.0 plus one commit) peers on `@astrojs/starlight >=0.42.0` and `astro >=7.2.10`. It validates internal links and hashes in Markdown and MDX during `astro build`, fails the build with a report, and invalidates the content-layer cache on every run, so its docs recommend enabling it conditionally. Options include `exclude`, `errorOnRelativeLinks`, `errorOnInvalidHashes`, `errorOnLocalLinks`, `errorOnFallbackPages`, `errorOnInconsistentLocale`, `sameSitePolicy`, `failOnError`, and `reporters`. Both HiDeoo docs sites enable it behind a `CHECK_LINKS` environment variable and exclude the blog listing pages. Sources: `packages/starlight-links-validator/package.json`, `docs/src/content/docs/getting-started.mdx`, and `docs/src/content/docs/configuration.md` at `b725855`; `HiDeoo/starlight-blog@19e7832` `docs/astro.config.ts`.

`[verified]` Starlight itself has no link checker; Astro has none either. `[recommendation]` Add `starlight-links-validator` 0.26.0 behind `CHECK_LINKS=1` and run `CHECK_LINKS=1 pnpm exec astro build` as the CI build, so local `docs:dev` stays fast and CI fails on a broken internal link. External links are out of scope for it and stay unchecked.
