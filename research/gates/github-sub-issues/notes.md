## REST contract

| Relationship | Read | Write | Meaning |
| --- | --- | --- | --- |
| Parent and child | `GET /issues/{child}/parent`, `GET /issues/{parent}/sub_issues` | `POST /issues/{parent}/sub_issues` with `sub_issue_id`, `DELETE /issues/{parent}/sub_issue` with `sub_issue_id` | [schema] Hierarchy and progress grouping, not execution order. |
| Blocked by and blocking | `GET /issues/{dependent}/dependencies/blocked_by`, `GET /issues/{blocker}/dependencies/blocking` | `POST /issues/{dependent}/dependencies/blocked_by` with blocking `issue_id`, `DELETE /issues/{dependent}/dependencies/blocked_by/{issue_id}` | [schema] Directed execution dependency. |

All table paths have prefix `/repos/{owner}/{repo}`. [Schema] The operations and parameters occur in the pinned [OpenAPI description](https://github.com/github/rest-api-description/blob/c6721f32a17a71397ae46be21be90d7f1a173b6e/descriptions/api.github.com/api.github.com.2026-03-10.json) and [sub-issue](https://docs.github.com/en/rest/issues/sub-issues) and [dependency](https://docs.github.com/en/rest/issues/issue-dependencies) endpoint references. List endpoints accept `per_page` up to 100 and `page`. A reader must follow `Link: rel="next"` until absent, then retain issue `id`, `number`, and `state`. The sub-issue add endpoint exposes `replace_parent`, which a trial must leave false.

[Documented] Read endpoints require Issues read for fine-grained tokens and write endpoints require Issues write. Public resources can be read without authentication. The documented read statuses include `200`, `404`, and `410`, with `301` also listed for parent and dependency reads. Add endpoints list `201`, `403`, `404`, `410`, and `422`, while remove sub-issue lists `200`, `400`, `403`, and `404`. A `404` parent response can mean no parent, as the live probe shows. An unknown response or partial page set must not become an empty dependency list. See the linked endpoint references and [evidence](evidence.md).

[Documented] [API versioning](https://docs.github.com/en/rest/about-the-rest-api/api-versions) identifies `2026-03-10` as supported and says an omitted header defaults to `2022-11-28`. [Rate-limit documentation](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) assigns most REST GET requests one secondary-limit point and most writes five, with endpoint-specific exceptions possible. Primary consumption comes from response headers, and rapid writes can trigger secondary limiting. Concurrent headers are snapshots, not a reliable request ledger.

[Inference] With one parent and `C` selected children, before, after, and rollback link checks need at least `3 × (1 + C)` GET requests. Adding and removing each selected link adds `2 × C` writes, for at least `3 + 5 × C` requests and about `3 + 13 × C` secondary-limit points under the documented default weights. Pagination adds GET requests. Capture `X-Ratelimit-Remaining`, `X-Ratelimit-Reset`, and `Retry-After` when present. [Documented] The [rate-limit guide](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) says a secondary limit may return `403` or `429`, so a write limit failure leaves restoration unresolved until the original link state is verified.
