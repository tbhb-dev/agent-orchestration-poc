# Codex session management: capabilities, persistence, and integration findings

Research date: September 26, 2026. Target: the installed Codex CLI and running local app-server, both version **0.157.1**, on macOS. Workspace: `/Users/tony/Code/github.com/tbhb/agent-session-tests`.

## 1. Main findings

Codex exposes enough structured interfaces to support a cross-harness session manager. The follow-up investigation exercised all 16 experiment categories originally listed as remaining, using disposable sessions and isolated data directories. The existing user daemon was queried read-only; restart, crash, migration, and deletion tests ran against separate test runtimes. Section 9 contains results, evidence labels, and limits.

The most consequential findings are:

1. **Thread, runtime, turn, and process lifetimes differ.** A turn can be interrupted while its background shell command continues running. A heartbeat test demonstrated this directly.
2. **Complete inventory requires descendant traversal.** Explicit source filters returned 73 of 108 stored threads in a follow-up snapshot. Ancestor-filter queries found all 35 missing spawned descendants, reconciling the entire snapshot.
3. **A second client can observe and control an existing live thread.** Metadata-only observation received status changes. Resume subscribed the second client to turn/item events and replayed pending requests; it could answer input, approve a harmless test command, and finish a pending dynamic tool after the first client disconnected.
4. **Writer ownership is scoped to the runtime.** A separate server saw `notLoaded` for a thread owned by the daemon and received an active-writer error on resume. After the test daemon stopped, the standalone server resumed the same thread and recalled its marker.
5. **History operations have distinct effects.** Resume preserved user and tool-output context. Fork retained selected history and shared the cwd, but received a new `sessionId` in this build. Revert replaced the rollout path, retained the file and paused goal, and could interrupt an active turn.
6. **Queue submission is not idempotent.** Reusing `clientUserMessageId` created another entry. Queue order and edits survived SIGKILL; resume automatically drained the surviving entries in order.
7. **Archive and delete affect descendants differently.** Archive cascaded to a spawned child; unarchive of the parent left the child archived. A dependent fork blocked parent deletion. Removing the fork allowed parent/child deletion and removed their logical database rows and rollout files, but identifier bytes remained in databases/logs.
8. **Usage is not additive across thread totals.** A fork inherited its source's cumulative usage. Response-level accounting measured 44,786 tokens of work where summing the source and fork totals would report 74,509. Compaction also emitted a `last` usage sample that did not represent a normal billable response increment.
9. **Version-specific testing is necessary.** An actual 0.156.1 → 0.157.1 migration preserved the thread, remembered marker, and paused goal. Generated schemas and live behavior differed from some public documentation descriptions.

This report studies Codex. It supplies comparison criteria for Claude Code and Gemini but does not claim their behavior has been tested. These are bounded observations on this installation, not universal lifecycle guarantees.

## 3. Identity and lifecycle model

### Native identities

| Entity | Evidence and meaning | Manager treatment |
| --- | --- | --- |
| Thread ID | Schema describes Codex-generated IDs as UUIDv7. Local environment `CODEX_THREAD_ID`, SQLite row, rollout metadata, and live API agreed for this thread. | Primary native conversation identifier; namespace by harness and installation/host. |
| Session-tree ID | The schema describes a session-tree identifier. Observed root, fork, and child each had `sessionId` equal to their own distinct thread ID; preserve native relationships rather than inferring shared lineage from this field. | Store separately; do not assume equality for forks or descendants. |
| Parent thread | `parentThreadId` represents subagent parentage in the schema. Local storage also has `thread_spawn_edges`. | Preserve an explicit parent relationship. |
| Fork source | `forkedFromId` represents conversation branching; the follow-up fork preserved this relationship. | Preserve separately from subagent parentage. |
| Turn ID | Schema and rollout records identify turns; the current turn has a `root_turn_id` as well. | Correlate input, output, usage, and completion at turn scope. |
| Item/call ID | Items and tool call/output records have IDs; tool outputs can reference `call_id`. | Join tool execution to its result; avoid counting multiple representations as separate work. |
| Client connection | `initialize` identifies an integration client. | Record observer/control connection identity separately from thread origin. |
| Command handle | The agent's execution tool can return a numeric `session_id` for a still-running command. | An ephemeral execution handle, not the persistent Codex thread ID. |

Observed research thread: `01a0de27-a994-7240-83ed-66d3abf28bbc`. Its persisted `source` was `vscode`, while rollout `originator` was `codex-tui`. The daemon handshake also reported a `codex-tui/0.157.1` user agent. These fields are useful metadata, but their labels are not proof of which UI is currently displaying or controlling a conversation. The generated schema explicitly describes `originator` as creation metadata, independent of the current client or executor. [L2–L6]

### Runtime status versus durable history

The generated `ThreadStatus` union contains:

- `notLoaded`: a thread not loaded in the queried runtime.
- `idle`: a loaded thread with no active turn indicated.
- `active`: includes `activeFlags`, which can contain `waitingOnApproval` and `waitingOnUserInput`.
- `systemError`: a runtime error state.

The separate `TurnStatus` enum contains `inProgress`, `completed`, `interrupted`, and `failed`. A completed turn does not mean the conversation is permanently finished. Archive state, goal state, runtime state, and last-turn outcome should remain separate fields. [L3]

The live daemon reported three loaded threads, including this research thread. This thread's status was `{"type":"active","activeFlags":[]}`. That verifies live observation of an existing active thread; it does not establish that every session on the machine belongs to this daemon. A separate standalone server or remote installation can have a different loaded set. [L6; inference]

Recommended state handling: preserve the native status and derive a UI status from it. On lost connectivity, show `unknown` or `disconnected`, with the timestamp of the last observation. Do not silently convert a stale active record to completed. File modification time and lockfile existence are insufficient evidence of current execution.

### App-server: recommended primary integration

The existing daemon socket was `/Users/tony/.codex/app-server-control/app-server-control.sock`. The managed executable reported by the daemon was `/Users/tony/.codex/packages/app-server-daemon/current/bin/codex`. [L2]

Transport was an important practical discovery. Sending JSONL directly through `codex app-server proxy` timed out during `initialize`. The proxy forwards bytes; the control socket expects a WebSocket connection. A standard HTTP Upgrade handshake over the Unix socket, followed by masked client WebSocket frames, succeeded. Direct `codex app-server` stdio uses JSONL, so those transports need different adapters. This is consistent with the [official protocol description](https://learn.chatgpt.com/docs/app-server). [L1, L6]

The successful request sequence was:

```json
{"id":1,"method":"initialize","params":{"clientInfo":{"name":"session_research","version":"0.1"}}}
{"method":"initialized"}
{"id":2,"method":"thread/loaded/list","params":{"limit":100}}
{"id":3,"method":"thread/read","params":{"threadId":"<thread-id>","includeTurns":false}}
```

Requests below were verified against the existing daemon without experimental opt-in:

| --- | --- |

A successful metadata read did not require taking control of the thread. The follow-up observed thread-status notifications on the metadata-only connection, but not turn/item events. Resuming the same thread on that connection enabled the fuller stream and pending-request replay. There is no evidence here of durable notification replay after arbitrary network gaps. [L8, E4]

## 5. Discovery and completeness

The generated list schema supports cursors, page size, sorting, source kinds, provider filters, exact cwd filters, archive selection, and title substring search. `sourceKinds` omitted or empty defaults to interactive sources. `archived:true` selects archived threads; false or omitted selects nonarchived threads. `searchTerm` is described as title matching, not transcript full-text search. [L3]

The broad source allowlist used in the successful probe was:

```json
["cli","vscode","exec","appServer","subAgent","subAgentReview","subAgentCompact","subAgentThreadSpawn","subAgentOther","unknown"]
```

At the first database snapshot there were 100 thread rows, with zero archived rows. Later, 101 rows were present, split into 49 legacy and 52 paginated histories. Other sessions and internal activity can change the store during inspection. The 30-versus-66 API difference conclusively demonstrates default filtering; the initial gap between 66 API results and the larger database population was not explained until the follow-up ancestor-filter experiment (E15). Internal subagent records exist in the database, including approval-review-related sources. The follow-up reconciled a later snapshot exactly: 73 broad results plus 35 unique descendants equaled 108 database rows. Ancestor traversal is required for complete discovery on this build. [L4, L6]

Recommended discovery procedure:

1. Identify each installation/home and runtime endpoint; record its current version.
2. Query stored threads with explicit source selection, paginate until the cursor is absent, and separately query archived threads. Enumerate spawned descendants with `ancestorThreadId` and deduplicate by ID; broad source filters alone omitted them in this build.
3. Query loaded threads on each runtime endpoint and annotate which runtime supplied the status.
4. Reconcile using IDs, not titles, cwd, timestamps, or process names.
5. Keep unsupported or unenumerated internal records distinct from user-manageable conversations.
6. Reconcile periodically after reconnects; do not infer deletion from one incomplete or filtered response.

`useStateDbOnly:true` was selected for the probes. The schema says ordinary listing can scan rollouts and repair thread metadata, whereas this option avoids that scan-and-repair path. It is useful for a minimally intrusive inventory, but it can trade completeness for lower impact when the index is stale. [L3]

## 6. Persistence and recovery boundaries

### Observed storage layout

The effective home for this session was `/Users/tony/.codex`. Treat that as an installation-specific value rather than a universal hard-coded path. [L4–L6]

| Artifact | Observed role or structure | Integration implication |
| --- | --- | --- |
| `sessions/YYYY/MM/DD/rollout-...jsonl` | This thread has a readable JSONL rollout. | Useful forensic/fallback input; native path is marked unstable in the protocol schema. |
| `state_5.sqlite` | Thread metadata and tables for spawn edges, projects, attachments, sections, and migrations. | Read-only fallback index; schema/version coupling is substantial. |
| `thread_history_1.sqlite` | Tables `thread_turns`, `thread_items`, projection state, and realtime items. | History is not confined to one transcript-file abstraction. Prefer API pagination. |
| `session_index.jsonl` | Sample keys: `id`, `thread_name`, `updated_at`. | Lightweight lookup data, not a full transcript or live-state feed. |
| `history.jsonl` | Sample keys: `session_id`, `ts`, `text`. | Separate input-history representation; do not assume complete conversation coverage. |
| `goals_1.sqlite` | Goal and continuation-deferral tables. | Durable objectives have separate storage. |
| `queue_1.sqlite` | Queued items and per-thread revisions. | Queue survival, order, edits, cancellation, and automatic draining after SIGKILL/resume were exercised; see E13. |
| `logs_2.sqlite` | Log database exists. | Diagnostics are a separate potential retention surface; contents were not investigated. |
| `thread-writer-locks/` | Per-thread lockfiles and a coordination lock exist. | Cross-runtime resume was rejected while another server held the writer; file existence alone still does not prove a live owner. |
| `app-server-control/` | Control socket and startup lock. | Endpoint discovery; connecting still requires permission and correct transport. |
| `app-server-daemon/` | PID/lock files, updater socket, and stderr logs. | Runtime bookkeeping; a stale PID file is not authoritative liveness. |
| `shell_snapshots/`, `memories/` | Present on disk. | Separate state categories; not verified as process checkpoints or conversation backups. |

SQLite WAL and shared-memory sidecars were present. Do not implement backups by copying only the main database while it is live. Use a consistent SQLite backup/snapshot procedure, and retain relevant artifacts together if building a recovery feature. Do not mutate native database rows to rename, archive, or delete sessions; use the supported protocol. These are implementation recommendations, not a tested Codex backup guarantee.

### Rollout record structure

This thread contained the following top-level record types: `session_meta`, `event_msg`, `response_item`, `world_state`, `turn_context`, and `token_usage_record`. `event_msg` included `task_started`, `item_completed`, and `token_count`. `response_item` included messages, custom tool calls/results, and reasoning records. [L5]

Selected structural facts:

- `session_meta` includes identity, creation metadata, cwd, version, source, history mode, session ID, instructions, and workspace roots.
- `turn_context` includes turn/root-turn IDs, model, cwd, date/timezone, collaboration mode, approval policy, and permission/sandbox configuration.
- Tool calls and outputs can be joined by `call_id`.
- Usage records include response, thread, session, turn, and root-turn identities, plus usage at response/turn/thread scopes.
- Reasoning records can include encrypted content. Their presence does not imply a readable complete reasoning trace.

A fallback parser should tolerate unknown record types, added fields, partial final lines, file replacement, and schema migrations. Track a file identity plus byte offset for incremental reads; avoid treating every modification as a brand-new transcript. API items, rollout response items, and event wrappers can overlap semantically, so ingesting all three without deduplication can inflate message and tool counts.

### What persistence does and does not establish

| State                    | Finding                                                                                                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Conversation history     | Stored thread metadata and persisted history are observed; resume interfaces are advertised. Restart/resume preserved both a user marker and a random value obtained only from tool output; see E1.                      |
| Workspace files          | Files live in the filesystem independently of thread history. Forking a thread is not evidence that files were copied or isolated.                                    |
| Configuration            | Schema supports per-resume overrides; turn context records execution settings. Never assume historical and effective settings are identical.                          |
| Model context            | Runtime instructions support automatic summarization/compaction, and the protocol exposes compaction. Full persisted history is not necessarily the next model input. |
| Goal                     | Separate durable schema/storage is observed; current goal is null.                                                                                                    |
| Queue                    | Queued entries survived SIGKILL and drained on resume. Duplicate client message IDs were accepted; exactly-once execution is not established.                                                                                              |
| Shell processes and PTYs | Tool handles exist while commands run. A background command survived turn interruption. Arbitrary shell-process restoration across runtime restart is not established.                                                                   |
| In-memory tool state     | Code cells and other kernels have their own lifetime. Conversation resume does not establish restoration of their variables.                                          |
| Cross-thread memory      | A separate memory facility exists in this environment. It is not the same thing as resuming the full transcript.                                                      |

## 7. Observability and interaction

### Available event families

The generated notification schema contains thread lifecycle/status events, turn start/completion, item start/completion, agent-message deltas, command output and terminal interactions, file-change events, plan/diff updates, token usage, goal changes, queue changes, and environment connection/disconnection events. Follow-up tests exercised delivery and pending-request replay within one runtime. General event replay across disconnects remains unproven. [L3]

Server-initiated request schemas include command/file-change approval, permissions approval, user input, MCP elicitation, and dynamic tool calls. A complete controlling client must handle bidirectional requests, not just consume assistant text. Runtime waiting flags can help an observer distinguish an active computation from a request awaiting a response. Automatic approval review is also represented in notifications, so a waiting or approval event should not automatically be labeled “waiting for a human.” [L3]

Recommended event adapter behavior:

- Preserve native thread/turn/item IDs, method name, source runtime, and timestamps.
- Distinguish response acknowledgments from later completion notifications.
- Retain unknown event variants instead of dropping or crashing on them.
- Re-read current state after a disconnect; do not assume stream delivery is durable or exactly once.
- Track pending interaction IDs, their resolution, and which client has authority to respond.
- Redact or avoid indexing message bodies, commands, tool results, and sensitive paths when only metadata is required.

### Usage and attribution

The generated usage notification has both `last` and `total` breakdowns. Counters include input, cached input, output, reasoning output, total, and cache-write input tokens. The local rollout also contains response-, turn-, and thread-level usage. [L3, L5]

A manager should not add cumulative totals repeatedly or double-count cached tokens as extra input. Store native counter semantics with each sample. Model and reasoning effort on thread metadata are explicitly described as current/latest configuration, not per-turn execution telemetry. Attribute historical usage using turn/response evidence when available. Token counts do not by themselves establish dollar cost, especially across subscription, API, provider, cache, and routing differences.

### Agent-visible capabilities in this session

This agent can inspect accessible local files, run commands, wait for running commands, write the report, and use the supplied conversation tools. It has no dedicated built-in global thread-list/resume/archive tool in its exposed tool catalog. The live inventory in this report came from shell access to the app-server protocol. [L7]

The environment also exposes collaboration tools for child agents, follow-up tasks, messages, interrupts, and agent listings. Those address an agent tree and are not a machine-wide historical session inventory. One disposable child was spawned inside an isolated test session to exercise descendant archive/delete behavior; no research work was delegated to other agents. Goal tools address the current thread's objective, not arbitrary session discovery.

The shell environment exposed `CODEX_THREAD_ID`, `CODEX_SANDBOX=seatbelt`, and disabled sandbox network access. These values can help correlate a process to a thread, but an inherited environment variable is a correlation hint, not authenticated proof of ownership. Avoid treating a process with a matching variable as authorized to control that conversation.

## 8. Proposed cross-harness manager design

This is a proposed adapter design, not an implementation delivered by this report.

### Common data model

| Record | Suggested fields |
| --- | --- |
| Installation | Harness, host ID, home/data root, executable, CLI version, runtime version, endpoint, authentication reference. |
| Conversation | Native thread ID, native session-tree ID, title, cwd/project, creation/update times, source/originator, parent ID, fork source ID, history mode, persistence mode, archive state. |
| Runtime observation | Endpoint, connection ID, native status, active flags, observed timestamp, freshness, control availability. |
| Turn | Native turn ID, parent/root correlation if supplied, start/end, native outcome, actual model evidence, usage, error. |
| Item/execution | Native item/call ID, tool type, status, process handle, timing, result reference. |
| Interaction | Approval/input request ID, requester, state, resolution, authorized responder. |
| Goal | Native objective/status, budget, usage, timestamps. |
| Capability | Supported, unsupported, unknown, or permission-blocked; evidence source and tested version. |

Use `(harness, host/installation, native_thread_id)` as a stable manager key. Retain native extensions instead of forcing all harnesses into identical lifecycle semantics. A thread can be archived, unloaded, and have a completed last turn simultaneously; a single flat status enum loses that information.

### Implementation sequence

1. **Observe:** build a Codex adapter for the existing app-server with explicit-source listing, archive enumeration, loaded-state inspection, metadata reads, and history pagination. Record coverage and freshness.
2. **Launch managed work:** add app-server start/turn execution or structured `exec` for tasks the manager owns. Capture native IDs immediately and record effective permissions.
3. **Add interactions:** route steering, interrupt, and approval/input responses using active-turn/request preconditions. Establish one control owner per thread as manager policy: native same-runtime clients can both submit input, and `turn/start` during an active turn steered that same turn in E4.
4. **Add lifecycle changes:** implement rename, fork, archive, and other mutations behind capability checks and explicit user actions. Keep deletion distinct from archive and filesystem cleanup.
5. **Add fallback ingestion:** read local metadata/transcripts when the runtime is unavailable, mark the result historical, and gate parsers by version/schema. Never manufacture live status from disk timestamps.
6. **Apply the same evidence framework to Claude Code and Gemini:** preserve their own persistence, identity, approval, and process semantics rather than assuming Codex behavior transfers.

Prefer a persistent protocol connection or periodic snapshots over repeated terminal UI scraping. For sessions started outside the manager, prioritize observation first: same-runtime second-client control was demonstrated, but a separate runtime must respect the native writer lock. Resume can also drain queued work, so attachment is not always passive.

Compaction used real turns plus one explicitly synthetic 600-line history item, rather than pretending that 600 real turns had occurred.

Evidence below refers to the `test` labels in [results.jsonl](session_experiments/codex/results.jsonl). Earlier failed or confounded attempts remain in the log; corrected observations are identified below. [L8]

### E1–E3: persistence, forks, and ephemeral threads

**E1 — Observed.** A first turn remembered `BLUE-ORCHID-741`. After server termination and restart, `thread/read` returned `notLoaded`; `thread/resume` restored the same ID and the next model turn returned the marker. Resume changed the effective sandbox to `readOnly` and approval policy to `on-request`. A separate stronger test generated a random file value, had the agent read it through a tool, deleted the file, restarted the server, and asked for the value without tools. The response matched exactly. Evidence: `initial_turn`, `restart_before_resume`, `resume_settings`, `resume_recall`, `tool_history_turn`, `tool_history_resume`.

**E2 — Observed.** Forking through the first completed turn included one historical turn, left the source at two turns, and preserved marker recall. The fork used the same cwd and saw the same scratch file. Both `id` and `sessionId` were new and equal to each other; `forkedFromId` pointed to the source. The spawned-child test also returned its own distinct session ID. This contradicts the blanket interpretation that every fork necessarily shares its root's session ID. Preserve `forkedFromId` and `parentThreadId` explicitly. Evidence: `fork`, `fork_turn_count`, `fork_recall`, `fork_filesystem`, `descendant_before_archive`.

**E3 — Observed.** An ephemeral thread had `ephemeral:true`, `historyMode:legacy`, and `path:null`. It completed a real turn and appeared in the loaded set. After restart it was unreadable, and direct checks found zero matching rows in the thread, turn, and item tables. Its ID remained in `logs_2.sqlite`. The early inventory probe mistakenly filtered for `appServer` while these app-server-created persistent test threads were classified `vscode`; that listing alone was not valid proof of ephemeral exclusion. The path, restart, and direct row checks supply the stronger evidence. Evidence: `ephemeral_start`, `ephemeral_turn`, `ephemeral_after_restart`, `ephemeral_residual_files`, `logical_rows_after_delete`.

### E4–E6: attachment, ownership, and steering

**E4 — Observed.** A second connection that only read metadata received `thread/status/changed` and account notifications, without turn/item output. After it resumed the same thread, it received start/completion events, message deltas, items, and usage. A pending dynamic-tool request was replayed with the same request ID. When the original client disconnected, the thread remained active and the second client resolved the tool request, allowing completion. Evidence: `read_only_observer_events`, `resumed_observer_events`, `pending_tool_replayed_to_second_client`, `owner_disconnect_status`, `second_client_tool_resolution`.

A second client's `turn/start` during an in-flight turn returned the original turn ID rather than creating an independent turn; the final answer included `SECOND-START-332`. Do not use `turn/start` as an assumed “start only if idle” primitive. A successful response is not proof that a new turn was created. Evidence: `concurrent_turn_start`, `concurrent_turn_completion`.

**E5 — Observed.** Both two standalone servers and a managed-daemon/standalone pair were tested against shared disposable storage. The owner reported the thread loaded; the other runtime had an empty loaded set and reported that same stored thread as `notLoaded`. Resume failed with `already has an active writer`. After stopping the isolated daemon, the standalone runtime resumed the same ID and recalled `DAEMON-552`. Status must be attributed to its runtime endpoint; `notLoaded` is not a host-wide liveness claim. Evidence: `other_runtime_read`, `other_runtime_resume`, `daemon_vs_standalone`, `standalone_after_daemon_stop`, `standalone_after_daemon_recall`.

The first managed-daemon attempt used an overly long scratch path and failed with `path must be shorter than SUN_LEN`. A shorter home path succeeded. Unix-socket path limits apply to manager-generated installations as well as protocol clients.

**E6 — Observed.** While a real turn waited at `lab_gate`, a stale `expectedTurnId` received error `-32600`, naming the expected and current IDs. A matching ID accepted new input. On releasing the tool, the model answered `GATE-DONE STEER-924`. Evidence: `steer_stale`, `steer_valid`, `steered_completion`. The explicit precondition is preferable to the implicit steering behavior of `turn/start`.

### E7–E8: interruption and pending interactions

**E7 — Observed.** `turn/interrupt` returned success and emitted a terminal turn with status `interrupted`. The initial process check still found the command PID alive, so a second test used a heartbeat to distinguish actual execution from a zombie or stale PID. After interruption, the heartbeat advanced from 5 to 15 over two seconds. The process remained a live Python process and appeared in `thread/backgroundTerminals/list`. It was then terminated explicitly. Files written before interruption remained. Evidence: `interrupt_completion`, `interrupt_process_effects`, `heartbeat_after_interrupt`, `heartbeat_cleanup`.

Manager consequence: expose “interrupt turn” and “terminate background command” as separate actions. This test establishes survival for a yielded/background command, not for every foreground command, child process, or signal pattern.

**E8 — Observed.** A Plan-mode turn invoked the native user-input tool. The thread reported `waitingOnUserInput`; a second client received the same request ID, supplied `BETA`, and the turn completed with `BETA`. The original client received `serverRequest/resolved`. A separate read-only thread requested approval for a harmless scratch-file write, reported `waitingOnApproval`, and accepted the second client's one-command approval. The file contained exactly `APPROVAL-OK`, and a resolution notification followed. No persistent execution-policy amendment was accepted. Evidence: `input_request`, `input_wait_status`, `input_broadcast`, `input_completion`, `input_resolved_events`, `approval_request`, `approval_wait_status`, `approval_file`, `approval_resolution_events`.

These tests establish multi-client resolution, not exclusive request ownership or exactly-once response semantics under racing replies. A manager should retire a pending prompt when it receives the resolution event, regardless of which client answered.

### E9–E11: history, compaction, archive, and deletion

**E9 — Observed.** After injecting one synthetic 600-line item and completing a real recall turn, `thread/compact/start` returned immediately. A `contextCompaction` item later completed. The history query retained the earlier turn IDs and added a compaction turn; a later model turn recalled the marker. The marker was also present in the synthetic item, so this is not a test of preserving every old detail through summarization. Automatic context-window exhaustion and maximum-scale history remain outside this sample. Evidence: `compaction_inject`, `compact_event`, `compaction_history`, `postcompact_recall`.

**E10 — Observed.** Reverting before the second turn removed that turn from the visible history while retaining the first. The scratch file and paused goal remained; an existing fork stayed readable. The returned rollout path changed to a replacement filename, and the returned `createdAt` also changed in this sample. Therefore, neither rollout path nor creation timestamp should be a manager's immutable identity key. Evidence: `revert`, `revert_effects`.

Reverting a turn that was actively waiting at `lab_gate` also succeeded and returned the thread idle. An early combined probe then timed out waiting for that discarded turn to complete. That timeout was a test-design error, not a failed revert; steering was repeated on a fresh turn without revert. Active revert must be treated as a disruptive history operation. Evidence: `revert_active` and the corrected `steered_completion`.

**E11 — Observed.** A real parent spawned one child, and both completed. Archiving the parent also archived the child. Unarchiving only the parent left the child archived. A separate fork of the parent prevented parent deletion with `forked history still references it`. After deleting that dependent fork, parent deletion succeeded, also removing the child. Both rollout files were gone, and thread/turn/item table queries returned zero matching rows. Evidence: `descendant_parent_turn`, `descendant_archived_ids`, `descendant_after_unarchive`, `descendant_delete_parent`, `delete_dependent_fork`, `delete_parent_without_fork`, `delete_cascade_final`, `logical_rows_after_delete`.

Archive and delete were also accepted while separate test threads waited at a dynamic tool. After archive the thread was unloaded and its rollout moved under `archived_sessions`; after delete it was unreadable. These operations are not limited to idle history management. Evidence: `active_thread/archive`, `active_after_thread/archive`, `active_thread/delete`, `active_after_thread/delete`.

A byte scan still found deleted identifiers in SQLite files, WAL files, and logs. This does not mean the deleted rows remained logically queryable; SQLite free pages and other references can retain bytes. It does establish that API deletion is not evidence of secure erasure. External files were not rolled back. Evidence: `deleted_id_residual_files` and `logical_rows_after_delete`.

### E12–E13: crashes and durable input queues

**E12 — Observed.** The stronger crash test killed the app-server with SIGKILL while its client remained connected and a model turn waited on a dynamic tool. After restart, metadata reported `notLoaded`; the historical turn reported `interrupted`, with null completion time and duration. No successful final answer was invented for that turn. A separate recovery test resumed its interrupted thread and completed a new `RECOVERED` turn. Evidence: `true_crash_status`, `true_crash_read`, `true_crash_turns`, `crash_recovery_turn`.

The first recovery probe closed clients before killing the server, which could itself influence interruption. Its findings were superseded by the connected-client SIGKILL test. Reconciliation through stored history worked; durable replay of every missed delta, request, or notification was not established.

**E13 — Observed.** Adding input to an idle thread could immediately consume it into execution. A controlled busy-thread test therefore held the thread at `lab_gate`, enqueued A and B, and submitted A again using the same `clientUserMessageId`. All three submissions received distinct queue IDs. Reordering all current IDs succeeded; an earlier incomplete reorder was rejected. B was edited, the original A was deleted, and the surviving duplicate A plus edited B remained in that order. Evidence: `queue_add`, `queue_reorder`, `busy_queue_duplicate`, `busy_queue_reorder`, `busy_queue_update`, `busy_queue_delete`.

Those entries survived the connected-client SIGKILL unchanged. After resume, the queue automatically produced completed turns answering `BUSY-A`, then `BUSY-B-EDITED`, and became empty. No explicit `thread/queue/start` was needed. An earlier explicit start attempt was rejected because auto-draining had already created an active/pending turn. Evidence: `busy_queue_before_crash`, `busy_queue_after_crash`, `busy_queue_resume`, `queue_final_history`.

Manager consequences: resume may cause queued execution; retrying a submission can duplicate work; queue IDs and client message IDs serve different purposes. This experiment does not establish exactly-once semantics when a crash occurs precisely between dequeue and externally visible side effects.

### E14–E16: usage, inventory, and migration

**E14 — Observed.** Two source turns used 14,850 and 14,873 tokens, totaling 29,723. A fork's new turn used 15,063, while its cumulative thread total was 44,786. Summing the two latest thread totals would report 74,509, double-counting the 29,723 inherited tokens. Per-response records identified the new work correctly as 44,786. Evidence: `usage_rollout_source`, `usage_rollout_fork`, `usage_reconciliation`.

Compaction emitted a sample with unchanged cumulative total, `last.totalTokens=21428`, and zero input/output counters. Do not treat every `last.totalTokens` notification as another model-response charge. Resume can also emit historical usage snapshots. Separate event observation from billable work attribution; deduplicate using native response identity and preserve counter scope. These measurements do not establish dollar cost. Evidence: `usage_events`.

**E15 — Observed.** The follow-up read-only snapshot contained 108 database threads. Broad API enumeration returned 73. All 35 missing rows were spawned descendants; the broad result already included guardian records. Three ancestor-filter queries returned overlapping descendant sets whose union contained exactly those 35 IDs. The API union then matched the full database snapshot. Evidence: `inventory_reconciliation`, `inventory_ancestor_filters`. The normal home was not mutated for this reconciliation, and unrelated thread contents were not recorded.

**E16 — Observed.** A real thread created and completed on installed 0.156.1 was opened by 0.157.1 using the same isolated home. The ID, paginated history, `UPGRADE-MARKER-682`, and paused goal survived. No installation was updated. Evidence: `upgrade_old_init`, `upgrade_old_turn`, `upgrade_new_init`, `upgrade_new_resume`, `upgrade_new_recall`, `upgrade_new_goal`.

Experimental-schema comparison found three added request methods (`account/gatewayOAuth/cancel`, `/login`, and `/read`) and no removed request methods. Selected start/resume/fork/list request top-level field sets were unchanged, but that is not full schema equivalence: a deeper comparison found new `startedAtMs` and `completedAtMs` properties on history item entries, plus an `explicitGatewayOauth` initialization capability. Migration evidence is limited to these two versions and the tested records, not rollback compatibility or every stored artifact.

### Corrections and limits of the experiment harness

The evidence preserves unsuccessful attempts rather than hiding them: premature subscription once returned `no rollout found`; waiting for a reverted turn timed out; incomplete queue reorder failed; an explicit queue start raced automatic draining; and the first daemon path exceeded the platform socket limit. Each was corrected by changing the experimental setup or recorded as observed behavior.

Early helper output collected all connection-level messages, which could include another queued turn or child. For conclusions about a particular turn, the authoritative `turn` object, native IDs, and thread-scoped usage records were used; later helper code filters message collection by thread. The source/fork accounting check uses rollout response records, not the mixed connection stream.

All original categories were exercised, but production-wide guarantees remain unproven: arbitrary network-loss replay, racing approvals, exactly-once external effects, filesystem restoration, all foreground/background process cases, disk-full/corruption recovery, very large histories, alternate providers, and other version migrations. These are limits on generalization of the completed experiments, not unperformed replacements for the original checklist.
