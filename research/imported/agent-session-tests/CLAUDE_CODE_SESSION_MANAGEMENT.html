Claude Code session management

How Claude Code identifies, persists, resumes, and exposes its sessions, written to inform a cross-harness session manager covering Claude Code, Codex, and Gemini.

Everything here was observed on this machine on 2026-09-26 against Claude Code 2.1.283 (native install, macOS), by reading ~/.claude/, running the CLI, and running a set of throwaway headless sessions to test identity, resume, fork, compaction, and hook behavior. Items marked (unverified) are inferred and were not directly tested. The on-disk formats are undocumented internals and change between versions: this machine has live sessions running 2.1.272 through 2.1.283, and records differ across them.

Key takeaways for a session manager

  1. Two ground-truth sources cover almost everything. ~/.claude/sessions/<pid>.json is a live registry of running interactive sessions with a status field. ~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl is the append-only transcript of every persisted session. A watcher on those two paths gives both live observability and history.
  2. claude agents --json is the supported way to list live sessions. It needs no TTY and returns the registry after checking which processes are still alive. Prefer it over parsing sessions/*.json yourself when you can afford to spawn a process.
  3. Hooks are the push channel. Every hook payload carries session_id, transcript_path, and cwd, and SessionStart reports why the session started (startup, resume, compact, clear). A small hook that forwards events to your manager is the most reliable real-time integration and does not depend on internal file formats.
  4. A session ID is not one conversation for the life of a process. /clear rotates the ID and starts a new file. --fork-session copies history into a new ID. /compact and --resume keep the ID. Plan the data model around conversations linked by lineage, not one ID per terminal.
  5. Retention is short on this machine. cleanupPeriodDays: 7 is set in ~/.claude/settings.json, and only 13 main transcripts survived across 30 project dirs when this investigation started. A manager that wants history must copy transcripts out on its own schedule.
  6. Headless -p sessions are invisible to the live registry and to history.jsonl. They only show up as transcripts, or through hooks and --output-format stream-json.

Identifiers

You can pick the ID up front with --session-id <uuid>, which is useful for a manager that launches sessions and wants to know the transcript path before the first byte is written. Inside a session the ID is available as $CLAUDE_CODE_SESSION_ID.

Names and titles

A session carries several human-readable labels, each recorded differently:

  • Registry name, as in agent-session-tests-26, with nameSource: "derived" (auto-generated from the directory plus a suffix) or "user". Set with -n/--name at launch. This is the name other sessions use to message this one.
  • custom-title record in the transcript, written when the user names the session.
  • agent-name record in the transcript.
  • ai-title record: an auto-generated summary title, rewritten as the conversation evolves (18 times in one 341-line transcript). The latest one wins. This session’s reads “Session management exploration and report”.
  • last-prompt record: the most recent user prompt plus leafUuid, used by the /resume picker.

How the ID changes across lifecycle events

Tested directly with headless sessions, and confirmed against existing transcripts for /clear:

Event Session ID Transcript file Evidence
New session New UUID (or --session-id) New file Test
--resume <id> / -c Same Appends to the same file Test: second turn appended to the same file, recalled the earlier message
--resume <id> --fork-session New New file holding a copy of the full history with sessionId rewritten Test: fork file had all prior turns; 21 record uuids were identical to the original
/compact (manual or auto) Same Same file; a system/compact_boundary record is appended Test plus existing transcript; SessionStart hook fires with source: "compact"
/clear New New file; the old one stops growing Existing transcripts: one process produced four files (805aa31c, then 2addad29, ae50f5df, f0842b0f), each new file starting with the /clear command record
--no-session-persistence (-p only) Assigned but ephemeral Nothing written Test

Lineage signals a manager can use, since there is no explicit parentSessionId field:

  • Fork: the fork shares record uuids with its source. Build an index of uuid → sessionId and treat overlap as a fork edge.
  • Clear: records in the new file carry session_id equal to the process’s original session. In the example above, every post-clear file has records with session_id: 805aa31c-…. The live registry also still lists the originating PID.
  • Compact: the compact_boundary record has parentUuid: null and a logicalParentUuid pointing at the last pre-compaction record, plus compactMetadata (trigger, preTokens, postTokens, preservedSegment).
  • Worktree: worktree-state records carry the sessionId of the session that created the worktree, which can differ from the current one.

Project directory encoding

The directory name is the absolute cwd with every / and . replaced by -, so /Users/tony/Code/github.com/tbhb/agent-session-tests becomes -Users-tony-Code-github-com-tbhb-agent-session-tests, and /private/tmp/.../-Users-... becomes -private-tmp-...--Users-.... The mapping is lossy and cannot be reversed. A literal - or . in the path is indistinguishable from a separator. Always take the real cwd from the cwd field on transcript records, or from the registry or hook payload.

Two further caveats:

  • Worktree sessions are filed under the parent repo’s directory. Session 756d25d7 ran in vale-ai-tells/.claude/worktrees/strained, and every record’s cwd is the worktree path, yet the transcript lives in -Users-tony-Code-github-com-tbhb-vale-ai-tells/. The transcript carries 28 relocated records (relocatedCwd = the main repo) and worktree-state records describing the worktree (worktreePath, worktreeBranch, originalBranch, originalHeadCommit). A worktree-state with a null worktreeSession marks leaving the worktree.
  • Project dirs are not exclusively Claude’s. -Users-tony-Code-github-com-tbhb-repotools--claude-worktrees-agy/ holds more than a hundred agy-explore-*.log files from some other tool. Filter on *.jsonl whose stem is a UUID.

Observed status values are busy (a turn is running), idle (waiting for the next prompt), and waiting (blocked on the user, such as a permission prompt or question). Timestamps are epoch milliseconds, while procStart is a human-readable string in UTC. The tmux field (session:@window.%pane) lets a manager jump straight to the pane.

Liveness caveats:

  • The file tracks the process, not the conversation. After /clear the registry’s sessionId should move to the new ID. (unverified) No live process was observed across a clear.
  • A crashed process can leave a stale file. Verify with kill -0 <pid> plus a procStart comparison, or delegate to claude agents --json, which does that check.
  • All eight registry entries seen were kind: "interactive", entrypoint: "cli". Headless -p runs never registered, and none of the test sessions appeared. Other values of kind and entrypoint, such as background, SDK, or IDE, were not observed. Transcript records from -p runs carry entrypoint: "sdk-cli" and promptSource: "sdk".
  • The sessionId in the registry can outlive a resumed conversation’s origin. PID 43574 was started with claude --worktree strained --resume 756d25d7-….

claude agents --json output (one element):

Transcript format

Envelope

Each line is one JSON object. Message-like records (user, assistant, attachment, system) share this envelope:

Field Meaning
type, subtype Record kind
uuid, parentUuid DAG link; parentUuid: null starts a chain (first message, or a compaction boundary)
logicalParentUuid On compact_boundary: the pre-compaction record it logically follows
sessionId Conversation ID
session_id Originating process session, present on a subset of records
timestamp ISO 8601 UTC
cwd, gitBranch Working directory and branch at the time of the record; gitBranch: "HEAD" outside a repo
version Claude Code version that wrote the record, so it can change mid-file after a resume on a newer binary
entrypoint cli, sdk-cli, and others
userType external
isSidechain true inside subagent transcripts
agentId Subagent transcripts only
isMeta Harness-injected rather than user-authored
promptId, permissionMode, promptSource, turnOrigin On user records
requestId, effort, perTurnEffort, apiBlockIndex, wireToolInputs On assistant records
toolUseResult, sourceToolAssistantUUID On user records that carry a tool result

The message field on user and assistant records is an Anthropic Messages API message (role, content blocks, and for assistant: model, stop_reason, usage). An assistant turn with several content blocks is split across several assistant records sharing one requestId and chained by parentUuid, so group by requestId to reconstruct API responses and to avoid double counting usage.

Cost and usage

Two sources:

  • Per request: assistant.message.usage has input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens (split into ephemeral_5m and ephemeral_1h), output_tokens_details.thinking_tokens, server_tool_use counts, and service_tier. It carries no dollar figure.
  • Running totals: the cost-state record, appended after turns, carries totalCostUSD, totalAPIDuration, totalAPIDurationWithoutRetries, totalToolDuration, totalLinesAdded, totalLinesRemoved, totalDuration, startTime, and modelUsage keyed by model ID with input, output, thinking, and cache token counts. Take the last cost-state in the file for session cost. It is cumulative for the process run, so check across resumes whether it resets (unverified).

~/.claude.json keeps the same kinds of last* totals per project, but only for the most recent session.

Subagents

The Agent tool writes each subagent to subagents/agent-<agentId>.jsonl beside the parent transcript, with the same envelope plus agentId, isSidechain: true, and the parent’s sessionId. The parent transcript’s tool result for the spawn (toolUseResult) includes agentId, status (such as async_launched), description, prompt, resolvedModel, isAsync, and outputFile, which is how to join parent and child. The .meta.json sidecar gives a summary without opening the transcript. Subagents are not sessions: they have no registry entry and no separate ID.

Hooks as an event stream

Hooks run a command with a JSON payload on stdin. The payloads below were captured by registering a logging hook for each event via --settings on a headless session, then resuming it with /compact:

Event Payload fields besides hook_event_name, session_id, transcript_path, cwd Observed values
SessionStart source; on resume also context_tokens, seconds_since_last_response, prompt_cache_likely_expired, estimated_cache_write_usd; on compact also model, prompt_id source: startup, resume, compact, (clear per docs, not tested)
UserPromptSubmit prompt, prompt_id, permission_mode
PreToolUse tool_name, tool_input, tool_use_id, prompt_id, permission_mode
PostToolUse as above plus tool_response, duration_ms
Stop last_assistant_message, background_tasks, session_crons, stop_hook_active, prompt_id, permission_mode End of each turn, the natural “went idle” signal
PreCompact trigger, custom_instructions, prompt_id trigger: "manual"
SessionEnd reason, prompt_id reason: "other" for a normal -p exit

Other events exist but were not captured here, including Notification (permission and idle prompts, useful for “needs attention”), SubagentStop, and PermissionRequest (unverified field lists).

Implications for the manager:

  • Registering hooks in ~/.claude/settings.json covers every session on the machine, including headless ones the registry misses. --bare disables settings hooks, so sessions launched that way are blind to this channel.
  • transcript_path saves reimplementing the lossy cwd encoding.
  • SessionStart then SessionEnd bracketing gives exact session lifetimes; a SessionEnd missing when the PID is gone means a crash.
  • Keep hooks fast and non-blocking: a hook that fails or hangs affects the user’s session. Appending to a file or writing to a socket and exiting is the safe shape.

Headless and SDK output

--output-format json returns one object with type: "result", subtype (success), session_id, num_turns, duration_ms, total_cost_usd, is_error, and result. --output-format stream-json --verbose emits a first system/init message with session_id, cwd, model, permissionMode, tools, mcp_servers, agents, skills, slash_commands, plugins, memory_paths, messaging_socket_path, claude_code_version, and more. That makes the init message a full capability snapshot of the session. --include-hook-events adds hook lifecycle events to the stream, which is an alternative to settings hooks when the manager is the one launching sessions.

Multi-session coordination

Claude Code already has a local peer layer, which a manager could observe or reuse:

  • Every interactive session exposes a Unix socket at /tmp/cc-socks/<pid>.sock, advertises peerProtocol: 1 and peerFeatures in its registry file, and holds a per-process peerToken in sessions/<pid>.<hash>.key. The protocol itself was not examined; treat the socket and token as private.
  • Inside a session, ListAgents lists the other local sessions by name, kind, status, tmux pane, and age, and SendMessage delivers messages to them. From this session it listed all seven peers, including one started two minutes earlier.
  • Agent teams (enabled here via CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1) write teams/session-<prefix>/config.json for every session, and every session is a team of at least one lead. Teammate messages queue in inboxes/<name>.json and are consumed on delivery.

Retention and cleanup

  • cleanupPeriodDays (7 here) prunes old transcripts and associated state. .last-cleanup records the last run (2026-09-26T14:12:20Z). Evidence: 30 project dirs, but only 13 transcripts remained, and file-history/ has five session directories.
  • Pruning appears to run at startup of any session, so data can vanish while the manager is not looking (unverified trigger).
  • claude project purge is the explicit per-project delete. --dry-run shows what would go.
  • Shell snapshots and session-env/ directories are not cleaned by purge.

Gotchas for the session manager

  1. Do not decode project directory names. Use cwd from records, the registry, or hook payloads.
  2. Transcript location does not equal cwd for worktree sessions (relocated).
  3. One process, many session IDs after /clear. Correlate with session_id on records and with the PID.
  4. One session ID, many processes over time through --resume, and version can change mid-file.
  5. Forks duplicate content. Deduplicate by record uuid, or history and cost figures double count.
  6. Assistant messages are split per content block. Group by requestId before summing usage.
  7. The registry misses headless sessions, and history.jsonl misses them too.
  8. Some stores key on an 8-char prefix of the session ID (tasks/, teams/), and some are not keyed by session at all (shell-snapshots/).
  9. Files are append-only but written live. Tail them and tolerate a partial last line.
  10. Formats are internal and version-specific. Key parsers on type and tolerate unknown types and fields; this machine alone shows at least 22 record types.
  11. Files are sensitive. Transcripts hold prompts, tool output, and pasted content; history.jsonl holds pastedContents; .key files hold peer tokens. Transcripts are mode 0600.
  12. The shell is macOS bash 3.2 for #!/usr/bin/env bash scripts unless a newer bash is installed, which matters for any helper scripts the manager ships (no mapfile, for example).

Suggested integration shape

  1. Discovery: poll claude agents --json, or watch ~/.claude/sessions/ with FSEvents or inotify, for live sessions and their status.
  2. Events: install a global hook for SessionStart, UserPromptSubmit, Stop, Notification, PreCompact, and SessionEnd that appends the payload plus a timestamp to the manager’s own log or socket.
  3. History: tail ~/.claude/projects/**/*.jsonl (UUID-named only) into the manager’s store, before cleanupPeriodDays removes them. Index by sessionId, record uuid, promptId, and requestId.
  4. Lineage: derive fork edges from shared uuids, clear edges from session_id and PID, and compaction from compact_boundary.
  5. Metrics: last cost-state per session for totals, turn_duration for per-turn latency, assistant.message.usage for per-request tokens.
  6. Control: launch with --session-id and --name so the manager knows identity up front, and use --resume, --fork-session, --bg, attach, stop, and rm for lifecycle. Use the tmux field to focus a pane.
