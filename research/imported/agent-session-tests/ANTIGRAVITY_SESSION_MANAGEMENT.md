# Antigravity Session Management

How Google Antigravity (AGY) identifies, persists, resumes, and exposes its sessions, written to inform a cross-harness session manager.

## 1. Key takeaways for a session manager

1. **The "Brain" is the ground truth.** Every session's state is fully persisted under `~/.gemini/antigravity-cli/brain/<conversation-id>/`. Unlike systems that spread state across hidden directories, all transcripts, generated artifacts, and scratch files live inside this one folder.
2. **Two transcript files.** `transcript.jsonl` is the compact log; `transcript_full.jsonl` contains the complete, untruncated payloads. For observability, you should tail these files.
3. **Hooks provide real-time events.** You can integrate a session manager by writing a custom hook (`hooks.json`) that listens to events like `PreInvocation`, `PostToolUse`, and `Stop`. Every hook payload carries the `conversationId` and `transcriptPath`.
4. **Resumability is native.** You can resume the most recent conversation using `agy --continue` (`-c`) or a specific conversation via `agy --conversation <conversation-id>`.
5. **Subagents fan out.** A single conversation can spawn multiple child sessions. Each subagent gets its own unique conversation ID and a fully isolated brain directory.

## 2. Session Identity & Core Storage

Every Antigravity session is uniquely identified by a UUID, the **Conversation ID**. 

### On-Disk Layout

All state for a given session is stored in the "brain" directory:
`~/.gemini/antigravity-cli/brain/<conversation-id>`

Inside this directory:
| Path | Scope | Purpose |
| --- | --- | --- |
| `.system_generated/logs/transcript.jsonl` | Per session | Compact JSONL transcript log. Large text fields may be truncated. |
| `.system_generated/logs/transcript_full.jsonl` | Per session | Complete JSONL transcript log. Never truncated. |
| `*.md` (Root level) | Per session | Artifacts generated by the agent (e.g., reports, summaries). |
| `scratch/` | Per session | Temporary data files, debug scripts, or code processing outputs. |

## 3. Transcript Format

The transcripts are JSON Lines (JSONL). Each line represents one "step" or action in the conversation.

### Record Envelope
Every JSON object in the transcript contains these core fields:
*   `step_index` (integer): Sequential index of the step.
*   `source` (string): The origin of the action, such as `USER_EXPLICIT`, `MODEL`, `SYSTEM`.
*   `type` (string): The type of step (e.g., `USER_INPUT`, `PLANNER_RESPONSE`).
*   `status` (string): Step status (e.g., `DONE`, `ERROR`).
*   `created_at` (string): ISO 8601 timestamp.
*   `content` (string): The text content (user request, model response, tool result).
*   `thinking` (string): Internal model reasoning (chain-of-thought) present in `PLANNER_RESPONSE` steps.
*   `tool_calls` (array): Tool calls made, including their arguments.
*   `media` (array): References to attached media files (mime_type and uri).
*   `truncated_fields` (array): Present **only** in `transcript.jsonl` if truncation occurred (e.g., `["content"]`). If present, the full content must be retrieved from the matching line in `transcript_full.jsonl`.

## 4. Multi-Agent & Subagent Management

Antigravity natively supports multiple autonomous agents working together. 
*   **Unique IDs:** Every invoked subagent gets a new conversation ID, creating a new brain directory and transcript.
*   **Inter-agent Communication:** Agents communicate via a built-in messaging system. The `send_message` tool delivers messages directly into the recipient's context, waking them reactively without polling.
*   **Workspace Branching:** Subagents can operate in shared workspaces or create isolated git branches (`Workspace: branch`) to experiment independently.
*   **Lifecycle Management:** Parent agents can list active subagents and their states (e.g., `running`, `idle`, `waiting_for_input`, `errored`) using the `manage_subagents` tool, and terminate them when necessary.

## 5. Extensibility and Hooks

Antigravity provides a deep customization system (Rules, Skills, Plugins, Hooks, MCP Servers). For a session manager, **Hooks** are the most powerful integration point.

Configured via `hooks.json`, they allow executing shell commands at specific lifecycle events:
*   `PreInvocation` / `PostInvocation`: Fired before/after the model is called.
*   `PreToolUse` / `PostToolUse`: Fired around specific tool executions (filterable via regex).
*   `Stop`: Fired when the agent execution loop terminates or pauses.

**Hook Payloads:** Every hook receives a JSON payload on `stdin` containing:
```json
{
  "conversationId": "...",
  "workspacePaths": ["/path/..."],
  "transcriptPath": "/path/.../transcript.jsonl",
  "artifactDirectoryPath": "/path/.../artifacts",
  "modelName": "auto"
}
```
This is the recommended way for a session manager to passively observe or actively steer an Antigravity session.

## 6. Remote Control and Shared Data

Antigravity surfaces (CLI, IDE, Desktop App) share the same `~/.gemini/antigravity-cli/` root data directory. 
*   **Daemon Mode:** `agy --remote-control` starts a daemon, allowing external tools to attach to the session.
*   **Shared Visibility:** A conversation started in the CLI can seamlessly be inspected, paused, or continued in the IDE because the state is unified on disk.

## 7. Suggested Integration Shape for the Session Manager

1.  **Discovery:** Scan `~/.gemini/antigravity-cli/brain/` for directories (UUIDs) to discover all historical and active sessions.
2.  **Liveness & Telemetry:** Tail `<conversation-id>/.system_generated/logs/transcript.jsonl` to observe the session in real-time, parsing the JSON for token usage, tool errors, and model reasoning.
3.  **Real-time Event Stream:** Deploy a global `hooks.json` that listens to the `Stop` and `PreToolUse` events to push status updates directly to your session manager.
4.  **Resume & Control:** Execute `agy --conversation <uuid>` to resume any paused conversation or spawn sub-tasks using the Antigravity SDK.
